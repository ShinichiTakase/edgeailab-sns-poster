## APIエンドポイント一覧

| メソッド | パス | 認証 | 概要 |
|---|---|---|---|
| GET | /api/billing/stripe-publishable-key | 不要 | Stripe公開鍵取得 |
| POST | /api/billing/payment-methods/setup-intent | requireAuth（管理者限定） | SetupIntent発行 |
| POST | /api/billing/payment-methods/confirm | requireAuth（管理者限定） | カード確定・優先度割当 |
| GET | /api/billing/payment-methods | requireAuth（管理者限定） | カード一覧取得 |
| DELETE | /api/billing/payment-methods/:paymentMethodId | requireAuth（管理者限定） | カード削除 |
| POST | /api/billing/payment-methods/swap | requireAuth（管理者限定） | プライマリ/バックアップ入替 |

全エンドポイントで`requireAdminRole`（`roleOf(req.user) === "管理者"`）を最初に
チェックし、それ以外は403 `forbidden`「お支払い方法の管理はアカウント管理者のみ
実行できます。」を返す。

## POST /api/billing/payment-methods/setup-intent

1. `ensureStripeCustomer`（未作成ならStripe Customer新規作成）
2. `stripe.paymentMethods.list`で既存カード数確認、2枚以上なら409 `card_limit_reached`
3. `stripe.setupIntents.create({customer, payment_method_types:["card"]})`
4. `{ clientSecret }`を返す

## POST /api/billing/payment-methods/confirm（body: `{paymentMethodId}`）

1. `stripe.paymentMethods.retrieve`で所有者確認（`pm.customer !== stripeCustomerId`
   なら403 `forbidden`）
2. **再度**`stripe.paymentMethods.list`でカード数を確認（今回追加した1枚を除いた
   `otherCount`）。SetupIntent発行〜確定の間に別タブで2枚目が追加されるレース
   条件への防御（コメントに明記）。`otherCount >= 2`なら**Stripe側の
   `paymentMethods.detach`で今回追加分を取り消し**、409 `card_limit_reached`
3. `priority = otherCount === 0 ? "primary" : "backup"`を`metadata.priority`に保存
4. `primary`の場合は`stripe.customers.update`で`invoice_settings.
   default_payment_method`を更新
5. カード詳細＋`priority`を返す

## GET /api/billing/payment-methods

1. `stripeCustomerId`未設定なら`{cards: []}`
2. `stripe.paymentMethods.list`＋`stripe.customers.retrieve`を並列取得
3. `resolvePriorities(list, defaultPaymentMethodId)`（下記）で優先度を解決

### 自己修復（drift-repair）ロジック（重要）
- `metadata.priority`が無く`default_payment_method`一致のみで暫定primary判定された
  エントリ（`isLegacyDefault`）は、この時点で`metadata.priority: "primary"`を
  書き戻す（バックフィル）
- 解決結果のprimaryのIDがStripe側`default_payment_method`と食い違っていれば、
  Stripe管理画面での直接編集等によるズレとみなし`stripe.customers.update`で
  再同期する

いずれも失敗時はログのみでレスポンスには影響させない（fire-and-continue）。
カードはprimary優先でソートして返却。

## DELETE /api/billing/payment-methods/:paymentMethodId

1. 所有者確認（403 `forbidden`）
2. `isLastCard = list.data.length === 1`
3. **409ルール**: `isLastCard && customer.stripeSubscriptionId &&
   !customerStore.isCanceled(customer)`なら409 `last_card_with_active_subscription`
   （解約済みアカウントは有効なサブスクリプションが無いため、最後の1枚でも削除可能）
4. 削除前に現在の`default_payment_method`・優先度を解決し、`deletedWasPrimary`判定
5. `stripe.paymentMethods.detach(paymentMethodId)`
6. 残枚数0なら`default_payment_method`をnullにクリア（削除カードの優先度に関わらず
   常にクリアし、ダングリング参照を防ぐ）
7. 削除されたのがprimaryで他に残りがあれば、残りの先頭を新primaryに昇格
   （`metadata.priority`更新＋`default_payment_method`更新）

## POST /api/billing/payment-methods/swap

1. `stripeCustomerId`未設定なら400 `swap_requires_two_cards`
2. 優先度解決後、`resolved.length !== 2`なら400 `swap_requires_two_cards`
3. 現primaryを`backup`に、現backupを`primary`に更新
4. `default_payment_method`を新primaryへ更新

## src/lib/paymentMethodPriority.js（resolvePriorities）

`GET /payment-methods`一覧・`invoice.payment_failed`Webhookのバックアップ再試行
ロジック双方が使う単一情報源:
1. 各PMについて`metadata.priority`（primary/backup）があればそれを優先
2. 無い場合、`pm.id === defaultPaymentMethodId`なら暗黙のレガシーprimary扱い
   （`isLegacyDefault: true`）。この分岐は、優先度・metadataの概念が導入される前の
   旧Stripe Checkoutのみのフローでオンボードした既存有償顧客（カード1枚のみ、
   metadata無しでStripeが自動的にdefault_payment_methodにセット済み）への対応
3. 上記2パスを経てもprimaryが1件も無い場合（`default_payment_method`が未設定、
   または既に削除済みのPMを指している完全に孤立したケース）、未決定の先頭カードを
   強制的にprimaryへ昇格させる（`isLegacyDefault: true`）。これが無いとUI上
   primaryが永久に0件になってしまうため
4. 残った未決定分は`backup`扱い（フェイルセーフ。通常は`/confirm`が必ず優先度を
   割り当てるためこの分岐は起きない想定、とコメントに明記）

## テスト（billing.paymentMethods.test.js、確認済みテスト名）

```
GET一覧: metadataのprimaryとStripe側default_payment_methodが食い違っている場合、
  default_payment_method側をmetadataに同期する（リグレッション対象）
DELETE: primaryタグの無いカード（backupのみ）を削除して0枚になった場合も、
  default_payment_methodをクリアする（リグレッション対象）
DELETE: primary削除でbackupが残っていれば、backupがprimaryに昇格し
  default_payment_methodも同期される
DELETE: 有効なサブスクリプションがある間、最後の1枚は削除できない（409）
POST swap: primary/backupを入れ替え、default_payment_methodも新primaryに同期される
POST swap: カードが1枚しかない場合は400
```

## microCMSスキーマへのI/O

読み取りのみ: `customers.stripeCustomerId`, `stripeSubscriptionId`, `status`
（カード情報自体はmicroCMSではなくStripe側が正）

## エッジケース・注意点

- カード情報自体はmicroCMSに一切保存せず、常にStripeを都度参照する設計
- `GET /payment-methods`は呼び出されるたびにStripe側とのズレを自己修復する
  （Stripeダッシュボードでの直接編集後もこのAPI呼び出しにより自動的に整合性が
  回復する設計思想。内部仕様として重要な前提）
- アカウント解約時（`routes/account.js`の`/api/account/cancel`）は、本ファイルの
  DELETEエンドポイントを経由せず、専用ロジックで登録済みカードを全件detachする
  （「最後の1枚は削除不可」制約の対象外。2026-08-22実装。詳細は内部仕様_解約.md参照）
