## データストア（json/announcements.json・json/announcement_reads.json）

`client_tokens.json`・`scheduled_post_retries.json`と同じくJSONファイルベースの
暫定実装（microCMSスキーマの手動追加を避けるため。件数も少ない想定）。両ファイルとも
`.gitignore`の`/json/`で除外済み。

- `announcements.json`: 配列。1件 = `{id, customerCode, type, title, body,
  createdAt}`。`type`は将来の拡張用（当面`"post_failure"`のみ発生）。
  `customerCode`は`req.customer.id`（microCMS顧客レコードid）。1顧客あたり
  `MAX_PER_CUSTOMER=200`件を超えたら古いものから切り捨てる（announcementStore.js）
- `announcement_reads.json`: `{ [userId]: 最終既読日時(ISO) }`。「未読件数は
  表示しない」仕様のため、既読済みID集合を持つ必要はなく、ユーザーごとの最終既読
  日時と対象顧客の最新お知らせの`createdAt`を比較するだけで未読有無を判定する
  （`hasUnread`）

## src/lib/postFailureAnnouncer.js（`announcePostFailure`）

投稿失敗を顧客向け「お知らせ」として記録する共通ヘルパー。**呼び出しは
「最終的に失敗が確定した時点」のみ**（再試行中の一時失敗では呼ばないこと）。

- `extractErrorDetail(err)`: ポスターモジュール（xPoster.js等）は`Error.message`に
  SNS APIの生エラー応答を`"何か: {JSON}"`の形で埋め込む（例:
  `tweet post failed: {"title":"Unauthorized",...}`）。message中の最初の`{`以降を
  JSONとしてパース検証し、成功すればそのJSON部分だけを、失敗すればmessage全体を
  そのまま使う
- `PLATFORM_DISPLAY_LABELS`: 既存の`invoiceSummary.js`・`oneShotPostResultMailer.js`・
  `scheduleResultMailer.js`・`posts.js`と同じ定義をこのファイルにも複製している
  （このコードベースの既存慣習に合わせた。共通化はしていない）
- 本文の「対象」行は、`scheduleName`が渡されれば`スケジュール「{name}」`、
  nullなら`ワンショット投稿`

## 呼び出し箇所

**src/routes/posts.js（ワンショット投稿、POST /api/posts）**: `postToPlatform`が
throwした`catch`ブロック内、`results[platform] = {ok:false, ...}`を設定した直後に
`announcePostFailure`を呼ぶ。再試行が無いため、この失敗が即・最終結果。

**src/scripts/scheduledPostRetryRunner.js（予約投稿の再試行、`exhausted`判定時のみ）**:
`retryStore.recordRetryFailure`が返す`entry.retryCount >= MAX_RETRIES`（3回）で
`exhausted`になった時点でのみ呼ぶ。通知メール（`sendScheduleResultEmail`/
`sendOneShotPostResultEmail`）の送信成否とは**独立に**呼ぶ
（`notify_email:false`でメールを送らない場合も、お知らせ自体は作成する。
2026-09-05設計判断）。`customerCache.get(post.customer_code)`が取得できない
場合（`attemptScheduledPost`がcustomer解決前に例外を投げたケース）は作成しない。

**scheduledPostRunner.js（予約投稿の初回実行）には組み込んでいない**
（初回失敗は必ず再試行されるため、ここで通知すると打ち止めになるまでに最大3件の
重複お知らせが発生してしまう。ユーザー要件として「最終的に失敗が確定した時だけ」を
明示的に選択した）。

## API

| メソッド | パス | 認証 | 概要 |
|---|---|---|---|
| GET | /api/announcements | requireAuth | 自顧客のお知らせを新しい順に返す |
| POST | /api/announcements/read | requireAuth | 自ユーザーの既読日時を現在時刻に更新 |

ロール制限ミドルウェア（blockViewerRole等）は挟まない（全ロールで操作可能という
要件のため）。

`GET /api/auth/me`のレスポンスに`hasUnreadAnnouncements`（真偽値）を追加
（`announcementStore.hasUnread(req.customer.id, req.user.userId)`）。サイドバーを
持つ全画面が既にこのエンドポイントを初期化時に呼んでいるため、専用のポーリング
エンドポイントを別途追加していない。

## フロント（js/role-nav.js・各画面）

`applyAnnouncementUnreadDot(hasUnread)`（role-nav.js）: `#announcements-unread-dot`
の`hidden`属性を切り替えるだけの薄い共通関数。`insertRoleNavItems`・
`applyPaymentGate`と同じく、サイドバーを持つ各画面のinit()内で
`/api/auth/me`取得直後に呼ぶ。

サイドバーを持つ全14画面（dashboard.html, onboarding.html以外の全画面
※onboarding.htmlのみサイドバー自体が無い）のサイドバーフッターHTMLに
「お知らせ」リンク（`announcements.html`、メールアイコンSVG、
`<span class="unread-dot" id="announcements-unread-dot" hidden>`）を
直接複製で追加している（このコードベースはサイドバーHTML自体がページごとの
静的複製であり、共通テンプレート化されていないため）。`change-password.html`は
従来`role-nav.js`を読み込んでいなかったため、この対応で新たに読み込むよう追加した。

`announcements.html`（新規画面）: 一覧取得後、`POST /api/announcements/read`を
呼んで既読化し、成功時は`applyAnnouncementUnreadDot(false)`でその場のドットも
消す。ホバーカードはCSSの`:hover`/`:focus-within`のみで開閉するシンプルな実装
（JS側の開閉状態管理は無い）。

## エッジケース・注意点

- 予約投稿で`attemptScheduledPost`が「SNS投稿失敗」以外の理由（`not_connected`・
  `account_canceled`・`trial_post_limit_reached`等）で例外を投げた場合も、
  区別せず同じ経路でお知らせを作成する（`Detail`欄がこれらのエラーコード文字列
  そのものになる。実用上は問題ないと判断し特別扱いしていない）
- 1顧客の複数ユーザー（チームメンバー）間で既読状態は独立（ユーザーごとに
  `announcement_reads.json`のキーが分かれる）。誰か1人が既読にしても他のメンバーの
  赤いドットは消えない
