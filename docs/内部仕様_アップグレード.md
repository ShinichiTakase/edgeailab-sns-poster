## POST /api/billing/create-checkout-session

1. `pricesForPlan(planKey(customer))`で`base`/`metered`/`meteredX`の3価格が揃って
   いることを確認（欠けていれば500 `plan_not_configured`）
2. `ensureStripeCustomer`
3. **`trial_end`の扱い（重要）**:
   - `MIN_TRIAL_END_LEAD_SECONDS = 2日+5分`
   - `customer.trialEndsAt`が「現在時刻+2日5分」より先なら、
     `subscription_data.trial_end`にそのままセットする
   - **理由**: `trial_end`をこの方法で設定すると`billing_cycle_anchor`が
     自動的に`trial_end`と同じ日付に設定される（実測確認済み）。以降の請求サイクルの
     月末日ズレ（1/31起点→2月は2/28、3月は3/31等）もStripe側が自動吸収するため
     独自ロジック不要
   - **Stripe Checkout Session経由での`trial_end`設定には「現在時刻より2日超先」の
     制約がある**（生のSubscriptions APIでは約60秒後でも許容されるが、本実装は
     Checkout経由のためこのより厳しい制約に従う。実際にCheckout Session作成を試して
     検証済み）。トライアル終了間際（2日以内）に決済登録された場合は`trial_end`を
     省略し即時課金にフォールバックする。CLAUDE.mdに記載の33日内部バッファ
     （`TRIAL_INTERNAL_BUFFER_DAYS`）は、まさにこの2日制約に余裕を持たせるために
     設けられている
4. `stripe.checkout.sessions.create`: `mode:"subscription"`, `customer`,
   `client_reference_id: req.customer.id`（Webhook側でmicroCMS顧客に紐付けるための
   キー）, `line_items:[base×1, metered, meteredX]`,
   `success_url: {base}/dashboard.html?billing=success`,
   `cancel_url: {base}/upgrade.html?billing=cancelled`
5. `{ url: session.url }`を返しクライアント側でStripeホスト画面へ遷移

## POST /api/billing/change-plan（body: `{targetPlan}`）

1. `PLAN_ORDER = ["basic","standard","advanced"]`で`targetPlan`の妥当性確認
   （不正なら400 `invalid_target_plan`）
2. 現在プランのインデックス取得（不明なら400 `invalid_current_plan`）
3. **ダウングレード禁止をサーバー側でも再検証**: `targetIndex <= currentIndex`なら
   400 `downgrade_not_allowed`「プランのダウングレードには対応していません。」
   （クライアント側のUI制御＝非活性ボタンは信用しない、とコメントに明記）
4. `stripeSubscriptionId`が存在する場合（既に本稼働中）:
   - 既存サブスクリプションアイテム3件を現在価格IDで特定し、対応する新プラン価格IDに
     マッピング
   - マッチしなかった場合は500 `subscription_items_mismatch`（データ不整合ガード）
   - **`stripe.subscriptions.update(subscriptionId, {items, proration_behavior:
     "none"})`＝日割り計算は一切行わない**。変更は即時反映されるが、請求は次回の
     通常更新時に新プランの金額で行われる（このリクエスト内では課金しない）
5. Stripe更新成功後、microCMSの`customer.plan`も更新。**Stripe成功後にmicroCMS書き込み
   のみ失敗した場合、Stripe側の変更はロールバックしない**（Stripe側は既に新プランで
   確定しているため）。この場合`200 {ok:false, error:"reflection_delayed", message:
   "決済は完了しましたが反映に時間がかかっています。しばらくして再度ご確認ください。"}`
   を返す
6. トライアル中（`stripeSubscriptionId`未設定）の顧客はStripe呼び出し自体をスキップし
   microCMSの`plan`のみ更新（実際のStripe Price適用は、実際にCheckout Session作成時
   に`pricesForPlan()`が新プランを参照することで自然に反映される）

## POST /api/billing/webhook

`express.raw({type:"application/json"})`使用（Stripe署名検証`stripe.webhooks.
constructEvent`が生bodyを要求するため、`express.json()`は使えない）。

### 処理するイベント種別（この2つのみ。他は全て黙って200を返す）

**`checkout.session.completed`**:
- `session.client_reference_id`（＝`req.customer.id`、Checkout Session作成時に
  セット）でmicroCMS顧客を特定
- `customerStore.updateCustomer(customerId, {stripeCustomerId: session.customer,
  stripeSubscriptionId: session.subscription, status:["active"]})`
- **`stripeSubscriptionId`が最初に書き込まれる唯一の箇所であり、`status`が
  `trial`→`active`に変わる唯一の箇所**
- `client_reference_id`が無ければ警告ログのみで何もしない

**`invoice.payment_failed`** → `handleInvoicePaymentFailed`（バックアップカード
自動再試行、下記）

### handleInvoicePaymentFailed（バックアップカード自動再試行ロジック）

1. `invoice.customer`からStripeカスタマーIDを解決、microCMS顧客を特定（見つからなければ
   何もしない）
2. **冪等性ガード（Webhook再送対策）**: `event.data.object`は生成時点のスナップショット
   であり再送時にも変化しないため、**必ずStripeから請求書を再取得**し、その最新
   `metadata.backup_retry_event_id`が今回の`event.id`と一致していれば処理済みとして
   スキップ。既に`status === "paid"`（バックアップ課金・顧客本人による支払い・過去
   イベントの手動再送等で既に解決済み）でもスキップ（`stripe.invoices.pay`を
   支払済み請求書に対して呼ぶとStripeがエラーを返し、誤った運用アラートの原因に
   なるため）
3. カード優先度を解決し`backup`カードを探す。無ければ「バックアップカード無し」として
   ログのみ、通常のStripeスマートリトライ（督促）に委ねてそれ以上は何もしない
4. backupカードがあれば`stripe.invoices.pay(invoiceId, {payment_method:
   backup.id}, {idempotencyKey: "invoice-backup-retry:{event.id}"})`
   - idempotencyKeyは**この特定のWebhookイベントの再送**のみを防ぐスコープ（Stripe
     自身の独立した督促リトライは別イベントIDで発生し、意図的にブロックしない）
   - **成功時**: 先に`invoice.metadata.backup_retry_event_id`へ`event.id`を
     書き込んでから通知メールを送信する順序（この書き込みが失敗すると通知メールが
     送られない可能性があるが許容。逆順にすると再送時の重複送信を防げなくなるため、
     「稀にメールが飛ばない」より「絶対に二重送信しない」を優先、とコメントに明記）。
     `BACKUP_CARD_CHARGED_EMAIL`を送信（件名「【EdgeAI Lab】お支払い
     （バックアップカード利用）のお知らせ」）
   - **失敗時**: それ以上の処理はせず通常の督促に委ねる。エラー種別が
     `StripeCardError`（単なるカード拒否）でなければ運用者宛に`notifyFailure`で
     アラート送信（予期しないStripe側エラーのみアラート対象、通常のカード拒否は
     アラート対象外）

### 上記以外のイベント種別
何もせず`200 {received:true}`を返す（Stripeのベストプラクティスに従い、関心のない
イベントでも常にACKしリトライを避ける）。署名検証失敗時は400。

## GET /api/billing/upcoming（外部仕様_ダッシュボード.mdと重複部分は要約、2026-08-26設計確定）

月選択パラメータは持たず、常に「今、進行中の1周期」だけを対象にする（「次回いくら支払うかを
知る機能であり、月を選ばないと金額が見えないのは本末転倒」というユーザー要件により、
旧・月選択プルダウン方式は廃止）。周期の境界はカレンダー月ではなく、Stripeの実際の請求
サイクル（`billing_cycle_anchor`基準）で解釈する。周期の投稿数は「予測投稿数 = 実績投稿数
（前回決算日〜今日）＋予定投稿数（今日〜次回決算日、現在のスケジュール設定が続いた場合）」
という1本の式に統一し、StripeのPrice tiersに当てはめて算出する（階層価格はStripeの実際の
`Price.tiers`を都度取得、ローカルにハードコードしない）。実額を`invoices.createPreview`から
そのまま取る（＝決済日より前の実績分しか反映されない）方式は採用していない。詳細は
内部仕様_ダッシュボード.md・内部仕様_請求.md参照。

**課金タイミングの整理（重要）**:
- 基本料金: **先払い方式**。決済日（次回決算日）に、その日から始まる次周期分を課金
  （サブスクリプションの`billing_cycle_anchor`＝`trial_end`を起点とした毎月の更新日）。
  レスポンスの`basicFeePeriod`でラベル「yyyy年mm月分」を付ける
- 従量料金・Xサーチャージ: **後払い＋予測方式**。前回決算日〜次回決算日の投稿実績＋予測に
  基づく（`invoiceSummary.js`の`derivePeriodKey`が確定済みinvoiceの請求明細の`period.end`
  から遡って`posting_logs`を参照する仕組みとは別物。そちらは確定済み請求の内訳表示専用）。
  レスポンスの`periodStart`/`periodEnd`でラベル「yyyy年mm月dd日〜yyyy年mm月dd日」を付ける
- 本稼働開始日を含む周期（トライアル終了直後の最初の請求）は基本料金のみ請求され、従量分は
  0（まだ実績が無いため）

## src/lib/stripePricing.js

- `planKey(customer)`: microCMSのselect形式（配列・先頭大文字）を小文字キーに正規化
- `pricesForPlan(plan)`: 環境変数`STRIPE_PRICE_{BASIC|STANDARD|ADVANCED}_
  {BASE|METERED|METERED_X}`から価格IDを解決
- `classifyPriceId(priceId)`: 全プラン×全カテゴリを横断して逆引き（過去にプラン変更
  した顧客の古い請求書明細も正しく分類するため、現在のプランだけでなく全プランを
  検索する）

## src/lib/stripeTierPricing.js

`computeGraduatedAmount(tiers, quantity)`: Stripeの段階制（graduated）課金計算を
ローカルで再現する純粋関数（予測専用）。**階層構造（単価・閾値）はローカルに
ハードコードせず常にStripeから都度取得**（`planLimits.json`・`surcharge.json`との
乖離を避けるための明示的な設計方針）。

## src/lib/planLimitsConfig.js / config/planLimits.json

`{"basic":1,"standard":3,"advanced":5}` — SNS接続可能数の上限（毎回ディスクから
再読み込み、キャッシュ無し）。

## src/lib/surchargeConfig.js / config/surcharge.json

`{"amount_jpy":32.0,"currency":"JPY","last_updated":"2026-08-15","unit":"per_post"}`
— 表示用のXサーチャージ単価。Stripe側の実際の価格変更時は本ファイルも手動同期が
必要（自動連携なし、とコメントに明記）。

## src/lib/meterEvents.js

`reportMeterEvent(eventName, stripeCustomerId)`: Stripeの新しいBilling Meters API
（`stripe.billing.meterEvents.create`、`usageRecords.create`ではない）で使用量
イベントを送信。`payload: {stripe_customer_id, value:"1"}`。投稿件数用・Xサーチャージ
用の2種類のメーターがあり、いずれも投稿成功のタイミングで1件ずつイベント発火される
（バッチ集計ではなくイベント単位でのリアルタイム報告）。Stripe未設定時は無音でスキップ。

## src/lib/stripeClient.js

`getStripe()`: `STRIPE_SECRET_KEY`未設定ならnullを返す（各所の「Stripe未設定」ガードの
基点）。`ensureStripeCustomer`: 既存`stripeCustomerId`があればそのまま返す、無ければ
`stripe.customers.create({email})`し永続化。

## src/scripts/addXSurchargePriceItems.js

手動実行（cron登録なし）の一回限り/随時実行スクリプト。デフォルトはドライラン、
`--apply`で実行。Xサーチャージ機能導入前から契約している既存顧客のStripe
サブスクリプションに、不足している`meteredX`アイテムを事後追加するための移行スクリプト。

## エッジケース・注意点

- プラン変更でStripe成功・microCMS失敗の不整合は自動ロールバックせず、`ok:false`
  レスポンスで顧客に「反映に時間がかかっている」旨を案内するに留める
- Webhookの冪等性は「イベント単位」であり、Stripe自身の独立した督促リトライ
  （別イベント）までは抑止しない設計
- ダウングレード禁止はUI・API双方で二重に担保されている

## 2026-10-04 Checkout作成の権限制御

`POST /api/billing/create-checkout-session`は管理者のみ許可し、他ロールはStripeアクセスより前に403を返す。解約済み顧客は403 `account_canceled`、既存の`stripeSubscriptionId`がある場合は409 `subscription_already_exists`として新規Checkoutを拒否する。初回の管理者Checkoutは従来の料金・税・トライアル設定を維持する。Webhookは引き続きraw bodyと署名検証を使用する。

この防御だけでは同時に作成される複数のCheckoutや、自動アクティベートの競合・DB反映失敗後の重複契約を保証できない。これらは別途冪等性・Stripe既存契約照合が必要。
