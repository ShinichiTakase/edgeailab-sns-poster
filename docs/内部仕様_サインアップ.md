## 公開ページからの登録導線（2026-10-01）

- index.htmlとpricing.htmlの共通登録リンクのhrefは`signup.html`。
- pricing.htmlのプラン別リンクは`signup.html?plan=basic`、`signup.html?plan=standard`、`signup.html?plan=advanced`。
- signup.htmlの既存の`URLSearchParams`と`VALID_PLANS`による初期選択を利用する。プラン未指定・不正値の場合は`standard`。
- 両ページから登録リンクのクリックを抑止していたメンテナンスモーダルとイベント処理を削除。

## APIエンドポイント一覧

| メソッド | パス | 認証 | 概要 |
|---|---|---|---|

## POST /api/auth/signup

### バリデーション（サーバー側、フロントと同一基準で再検証）
- メール形式、パスワード要件（英大文字・英小文字・数字・記号を各1文字以上、8文字以上）、
  お名前必須（フロント側の「3文字以上」制限はサーバー側では未実装。要確認: サーバー側は
  空文字チェックのみで、3文字未満でも通過しうる）

### 処理フロー
1. `customerStore.getCustomerByEmail`で重複確認。既存レコードがあり`status`が`canceled`
   以外なら409 `email_exists`
2. 既存レコードが`canceled`の場合のみ`reactivateCustomer`で再アクティブ化（新規レコードは
   作らない。同一メールでの再サインアップによる無料トライアル再取得の抜け穴を塞ぎつつ、
   正規の再契約は妨げないための分岐。2026-08-22までは`reactivateCustomer`の実装が
   この意図に反してトライアルを再付与してしまっていたが修正済み。詳細は
   内部仕様_無料で始める（トライアル）.md・内部仕様_解約.md参照）
3. パスワードをbcrypt（`BCRYPT_ROUNDS=12`）でハッシュ化
4. 24時間有効な`verificationToken`を発行
5. `trialEndsAt`を現在時刻+33日（TRIAL_DAYS+TRIAL_INTERNAL_BUFFER_DAYS）で計算
   （※`reactivateCustomer`はこの値を受け取っても内部で無視し、常に空にする。
   新規`createCustomer`のみがこの値を実際に使う）
6. `customerStore.createCustomer`（新規）または`reactivateCustomer`（再契約）でmicroCMSに書き込み
7. `VERIFICATION_EMAIL`テンプレートで認証メールを送信（送信失敗してもサインアップ自体は
   失敗させず、warnログのみ）
8. サインアップ完了直後からダッシュボードを表示するため、メール未認証のままJWTセッションを
   発行しCookieにセットする（機能制限は`isVerified`で別途ガード。requireVerified参照）
9. レスポンスに`requiresPayment: Boolean(existing)`を含める。既存レコードの再利用
   （＝解約後の再登録）だった場合は`true`となり、フロント側（signup.html）はこれを見て
   `dashboard.html`ではなく`upgrade.html?reason=payment_required`へ直接遷移する
   （2026-08-22追加。再登録者が支払い未登録のまま操作を進めて後から各所でブロックされる、
   という不自然な導線を避けるため）

### createCustomer（customerStore.js）が書き込むmicroCMS customersフィールド
```
slug: crypto.randomUUID()（内部識別子。json/client_tokens.jsonのキーにも流用）
email, contactName, companyName
status: ["trial"]
plan: [Basic|Standard|Advanced]（先頭大文字の選択肢形式）
verificationToken, verifyExpiresAt, trialEndsAt
users: [{ userId: uuid, email, passwordHash, role: ["管理者"] }]
```

### reactivateCustomer（既存レコード再利用時）が上書きするフィールド（2026-08-22修正後）
```
email, contactName, companyName
status: ["active"]   // "trial"にはしない（2026-08-22修正前は"trial"だった）
isVerified: false
verificationToken, verifyExpiresAt
trialEndsAt: ""       // 常に空（呼び出し元が渡すtrialEndsAtパラメータは無視する）
trialPostCount: 0
trialReminderSent: false
stripeSubscriptionId: ""
users: [新しい管理者ユーザー1名のみに置き換え]（要確認: 旧usersに含まれていた招待メンバーは
  この時点で全員失われる。仕様として意図的か、実装上の見落としかはコードから断定できない。
  今回の調査・修正の対象外）
```
customers.statusのselect選択肢はtrial/active/canceledの3つしか定義されていないため
（microCMS管理画面側の変更が必要でコードからは追加不可）、「トライアルなし・未払い」を
表す専用の値は使わず既存の"active"を流用している。実際のアクセス制限は
`requiresPaymentRegistration()`が担う（内部仕様_無料で始める（トライアル）.md参照）。

## GET /api/auth/verify

1. `?token=`が無ければ`verify-pending.html?error=missing_token`へリダイレクト
2. `customerStore.getCustomerByVerificationToken`でトークン一致するレコードを検索。
   無ければ`?error=invalid_token`
3. `verifyExpiresAt`（24時間）を経過していれば`?error=expired_token`
4. `markVerified`で`isVerified: true`、`verificationToken`・`verifyExpiresAt`をクリア
5. JWTセッションを再発行してCookieにセットし、`dashboard.html`へリダイレクト（自動ログイン）

## POST /api/auth/resend-verification

- メールアドレス単位で60秒（`RESEND_MIN_INTERVAL_MS`）のレート制限（インメモリMap。
  複数インスタンス構成では効かない点に注意。要確認: 現行は単一コンテナ運用のため実害なし
  と思われるが、スケールアウト時は要見直し）
- 存在しないメール・認証済みメールのいずれも同一の成功レスポンス（`{ok: true}`）を返し、
  登録有無を外部から判別できないようにしている
- 新しい`verificationToken`を発行して上書き（古いトークンは自動的に無効化される）

## セッション（jwt.js）

- Cookie名: `sns_poster_session`（httpOnly, secure, sameSite=lax, 30日）
- JWTペイロード: `{ sub: customer.id, userId, email, sessionVersion }`
- `sessionVersion`はusers[].sessionVersionのスナップショット。パスワード再設定等で
  インクリメントされると、発行済みの旧JWTは`requireAuth`のバージョン比較で一括失効する
  （express-session等のサーバー側ストアを持たないステートレス方式のため、これが唯一の
  全セッション無効化手段）

## 外部SaaS連携

- メール送信のみ（`customerMailer.js` → SMTP、ホストのpostfix 127.0.0.1:25宛）。
  Stripe等の決済系連携はサインアップ時点では発生しない（外部仕様_アップグレード.md参照）

## エッジケース・注意点

- 解約済みアカウントの再サインアップ時、招待済みメンバー情報が失われる可能性がある（上記参照）
- サーバー側のお名前バリデーションがフロントより緩い（空文字のみ拒否）
- メール送信失敗時もサインアップ自体は成功として扱われる（ユーザーは認証メールが届かないまま
  ダッシュボードに到達でき、verify-pending.html等から手動再送信する必要がある）
