## GET /api/auth/me が返す主なフィールド（ダッシュボードでの用途）

```
email, contactName, plan, isVerified, trialEndsAt, trialDisplayEndsAt, status,
trialPostLimitReached, coins, nextBillingDate, connectedPlatforms, user: { email, role }
```
`plan`はサインアップ機能で解説の`safeCustomer()`が生成。`user.role`はロール別ナビ挿入・
プロフィールメニューの解約ボタン表示判定に使用。`trialPostLimitReached`（2026-08-25
追加）はトライアル投稿上限到達バナー表示判定用（外部仕様・内部仕様_無料で始める
（トライアル）.md参照）。

## GET /api/posts/stats（投稿実績ウィジェット）

- `requireAuth`のみ（読み取り専用のため`requireVerified`等のガード無し）
- クエリ`year`,`month`（整数、month 1-12）不正なら400 `invalid_year_month`
- `postingLogStore.getPostStatsForCustomer(customerId, year, month)`:
  - `billingPeriod = "YYYY-MM"`文字列で`posting_logs`を`customer_code[equals]X[and]
    billing_period[equals]YYYY-MM`フィルタ
  - プラットフォーム別件数を集計（`billing_period`は投稿記録時に刻印された文字列であり、
    トライアルサイクル等とは独立した単純な暦月集計）
- レスポンスは`{x,threads,facebook,instagram}`をラップせずそのまま返す

## 「月」の基準はカレンダー月ではなくStripeの実請求サイクル（2026-08-26設計変更）

投稿予定ウィジェット・ご請求予測ウィジェットは、共通ロジック
[billingCycle.js](../src/lib/billingCycle.js)を介して、`month`パラメータ（カレンダー年月）を
「その月に決済日（Stripeが実際に請求を確定するタイミング）が来る周期」に対応させて計算する。
カレンダー月そのもので集計する旧実装は廃止した。

- **アンカー（基準時刻）**: `getBillingCycleAnchor`が、既にStripeサブスクリプションが
  存在する顧客は実際の`subscription.billing_cycle_anchor`を取得して使う。
  `customer.trialEndsAt`は決済登録後もクリアされず残り続ける内部値であり、実際の
  請求サイクルとズレていた実例が見つかったため、本稼働済みの顧客には使わない
  （実機で確認、2026-08-26）。まだCheckout未完了（トライアル中）の顧客のみ、
  `trialEndsAt + 1日`を将来のアンカー予測値として使う。
- **周期の進め方**: `addStripeStyleMonths(anchor, n)`が、Stripeの実際の月次課金アンカーの
  挙動（日単位・当月に該当日が無ければその月の最終日に丸める。例: 起点1/31なら2月は2/28、
  3月は3/31）を再現する。「歴月30日固定」でも「存在しない日は翌日に繰り越す」でもなく、
  **実際のStripeの挙動に合わせる**方針（要件定義時にユーザーが明示的に選択）。
- **周期番号n**: `findCycleIndexForMonth`が、対象カレンダー年月に決済日が属する周期番号n
  を求める（n=0が最初の決済＝本稼働開始日）。月次サイクルのため該当月には必ずちょうど1つ
  決済日が存在する。

## GET /api/billing/next-cycle（プルダウンの開始年月、2026-08-26追加）

投稿予定・ご請求予測ウィジェットの月選択プルダウンが起点にする年月を返す
（`{year, month}`）。「ご請求予測は次回いくら支払うかを知るための機能であり、既に決済済みの
周期を選択肢に出しても意味がない」というユーザー要件により、`findNextUnbilledCycleIndex`が
決済日がまだ来ていない直近の周期（＝次回決済）を求め、その周期の年月を返す。フロント側
（dashboard.htmlの`populateFutureMonthSelect`）はこの年月からプルダウンの選択肢12ヶ月分を
生成する（＝既に決済済みの月はプルダウンに出てこない）。

## GET /api/posts/scheduled（投稿予定ウィジェット、2026-08-26設計変更）

- `requireAuth`のみ。`month`パラメータは`YYYY-MM`形式必須（400 `invalid_month`）、
  過去月は400 `month_in_past`
- 対象月に決済日が属する周期番号n（`findCycleIndexForMonth`）を求め、n<0なら空カウント。
  n=0（トライアル中でまだ一度も決済していない）はサイクル開始点が定義できないため、
  「今日から初回決済日まで」の予測分のみを使う
- レスポンスは`billingCycle.getCombinedPostCounts`の`counts`のみ（プラットフォーム別、
  下記参照）。以前のように`scheduled_posts`（cronに登録済みの予約）の件数をそのまま
  数える実装ではない

## GET /api/billing/upcoming（ご請求予測ウィジェット、2026-08-26設計変更）

`month`パラメータの検証は上記と同一。Stripe未設定なら500 `stripe_not_configured`、
プラン価格未設定なら500 `plan_not_configured`。

### 先払い（基本料金）・後払い＋予測（従量料金・Xサーチャージ）

- **n<0**（本稼働前）: 全項目0円
- **n=0**（最初の決済月）: 基本料金のみ（従量分の対象期間がまだ存在しないため）
- **n≧1**: 基本料金＝この決済日から始まる次周期分（先払い）。従量料金・Xサーチャージ＝
  `billingCycle.getCombinedPostCounts(customer, cycleStart, cycleEnd)`が算出する
  「その周期の投稿数（実績＋予測の合算）」を、StripeのPrice tiers
  （`computeGraduatedAmount`、単価・閾値はハードコードせずStripeから都度取得）に
  当てはめて算出する

### 投稿数の合算方式（`getCombinedPostCounts`、投稿予定ウィジェットと共通）

「ご請求予測は次回いくら支払うかを知るための機能。次回決済日より後の月を選ばないと
金額が見えないのでは意味がない」というユーザー要件により、対象周期の投稿数は
「今日までの実績＋今日から決済日までの予測」を合算する（実額をStripeの
`invoices.createPreview`からそのまま取るだけの旧実装は廃止。段階制tiersの閾値を
跨ぐ計算を正しく行うため、実績・予測とも「金額」ではなく「件数」の時点で合算してから
tiersに当てはめる）。

- **実績（`postingLogStore.getActualPostCounts`）**: 周期開始日〜今日（`min(now, cycleEnd)`）
  の`posting_logs`（実行済み投稿）を実際の投稿日時（`posted_at`）で範囲集計する
  （`billing_period`という歴月単位フィールドではなく、`posted_at[greater_than/less_than]`
  で絞り込む専用関数`listPostingLogsForCustomerInRange`を使う）
- **予測（今日〜決済日）**: 「現在のスケジュール設定が続いた場合」の見積もりを2種類合算
  - 単発予約（`scheduledPostStore.getScheduledPostsSummary`。status=pendingの
    `scheduled_posts`を対象期間で範囲集計。旧実装は歴月単位だったが、任意の日時範囲を
    受け取れるよう改修した）
  - 繰り返しスケジュール（`getScheduleForecastForCustomer`→`estimateScheduleFirings`の
    シミュレーション。プラットフォーム別内訳counts・xUrlCount・totalCountを返すよう
    拡張した。post_schedulesの実データは書き換えない）
- 周期がまるごと未来（`cycleStart > now`）なら実績部分は自動的に空、まるごと過去
  （`cycleEnd <= now`。通常は起こらない）なら予測部分は自動的に空になる

いずれも`{basicFee, usageFee, xSurcharge, total, isEstimate: true}`形式で返す。

## GET /api/billing/x-surcharge（Xサーチャージ情報カード）

認証不要の公開エンドポイント。`config/surcharge.json`の内容をそのまま返す。

## GET /api/sns-connections（SNS連携状況）

`requireAuth`のみ。詳細は内部仕様_SNS連携.md参照。フロント側コメントには「連携数・
上限判定はサーバーの応答を必ず信頼し、フロント側で独自に計算し直さない」という方針が
明記されている。

## エッジケース・注意点

- 投稿実績・投稿予定・請求予測のいずれも、API失敗時はフロント側で「－」を表示するのみで
  エラーバナー等は出さない設計（ウィジェット単位で独立してサイレントフェイルする方針）
- SNS連携状況・Xサーチャージ情報も同様に、取得失敗を握りつぶして他機能に影響させない
  設計が随所に採用されている（コード内コメントで繰り返し明記されているパターン）
