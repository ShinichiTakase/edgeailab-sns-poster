## GET /api/auth/me が返す主なフィールド（ダッシュボードでの用途）

```
email, contactName, plan, isVerified, trialEndsAt, trialDisplayEndsAt, status,
trialPostLimitReached, coins, nextBillingDate, connectedPlatforms, user: { email, role }
```
`plan`はサインアップ機能で解説の`safeCustomer()`が生成。`user.role`はロール別ナビ挿入・
プロフィールメニューの解約ボタン表示判定に使用。`trialPostLimitReached`（2026-08-25
追加）はトライアル投稿上限到達バナー表示判定用（外部仕様・内部仕様_無料で始める
（トライアル）.md参照）。

## 「今、進行中の1周期」という考え方（2026-08-26確定）

投稿実績ウィジェット・ご請求予測ウィジェットは、共通ロジック
[billingCycle.js](../src/lib/billingCycle.js)の`getCurrentBillingCycle(stripe, customer)`を
介して、常に「今、進行中の1周期」だけを扱う。**どちらのウィジェットも月選択プルダウンは
持たない**（〜2026-08-25の実装は月選択プルダウン＋歴月/周期ベースの集計だったが、
「ご請求予測は次回いくら支払うかを知るための機能であり、月を選ばないと金額が見えないのは
本末転倒」というユーザー要件により廃止した）。

- **周期の境界はカレンダー月ではなくStripeの実請求サイクル基準**（`billing_cycle_anchor`）。
  `getBillingCycleAnchor`が、既にStripeサブスクリプションが存在する顧客は実際の
  `subscription.billing_cycle_anchor`を取得して使う。`customer.trialEndsAt`は決済登録後も
  クリアされず残り続ける内部値であり、実際の請求サイクルとズレていた実例が見つかったため、
  本稼働済みの顧客には使わない（実機で確認、2026-08-26）。まだCheckout未完了（トライアル中）
  の顧客のみ、`trialEndsAt + 1日`を将来のアンカー予測値として使う
- **周期の進め方**: `addStripeStyleMonths(anchor, n)`が、Stripeの実際の月次課金アンカーの
  挙動（日単位・当月に該当日が無ければその月の最終日に丸める。例: 起点1/31なら2月は2/28、
  3月は3/31）を再現する。「歴月30日固定」でも「存在しない日は翌日に繰り越す」でもなく、
  **実際のStripeの挙動に合わせる**方針（要件定義時にユーザーが明示的に選択）
- **`getCurrentBillingCycle`の戻り値**: `{ n, cycleStart, cycleEnd }`。`n`はまだ決済が
  完了していない直近の周期番号（決済日が現在時刻以降の最小のn。本稼働前ならn=0）、
  `cycleEnd`は次回決算日（次回決済日）、`cycleStart`は前回決算日（前回決済日）。
  **`n===0`（本稼働前・トライアル中でまだ一度も決済していない）は`cycleStart`が
  `null`になる**（前回決算日が存在しないため）。アンカーそのものが定まらない
  （サブスクリプションもtrialEndsAtも無い）異常系は関数自体が`null`を返す

## GET /api/posts/stats（投稿実績ウィジェット、2026-08-26設計変更）

- `requireAuth`のみ。クエリパラメータは無し（常に「今、進行中の周期」の実績のみを返す。
  旧実装の`year`/`month`クエリ・`billing_period`歴月集計は廃止）
- `getCurrentBillingCycle`で周期を求め、`cycleStart`が無ければ（本稼働前）空カウントを返す
- `postingLogStore.getActualPostCounts(customerId, cycleStart, now)`:
  - `posted_at[greater_than/less_than]`で実際の投稿日時により範囲集計する専用関数
    `listPostingLogsForCustomerInRange`を使う（`billing_period`という歴月単位フィールドは
    使わない。周期境界がカレンダー月と一致しないため）
  - プラットフォーム別件数を集計
- レスポンス: `{ counts: {x,threads,facebook,instagram,linkedin}, periodStart, periodEnd }`
  （`periodStart`=前回決算日のISO日時、`periodEnd`=リクエスト時点の「今日」のISO日時。
  いずれも本稼働前は`null`）。フロント側はタイトルに
  `投稿実績（<periodStartをyyyy年mm月dd日形式に整形>〜<periodEnd同上>）`と付記する

## GET /api/billing/upcoming（ご請求予測ウィジェット、2026-08-26設計変更）

- `requireAuth`のみ。クエリパラメータは無し（常に「今、進行中の周期」の予測のみを返す）
- Stripe未設定なら500 `stripe_not_configured`、プラン価格未設定なら500 `plan_not_configured`

### 先払い（基本料金）・後払い＋予測（従量料金・Xサーチャージ）

`estimateBillingForecast(stripe, customer, prices)`:

- `cycleStart`が無い（本稼働前）: 基本料金のみ（従量分の対象期間がまだ存在しないため）
- `cycleStart`がある: 基本料金＝この決済日（`cycleEnd`）から始まる次周期分（先払い）。
  従量料金・Xサーチャージ＝`billingCycle.getCombinedPostCounts(customer, cycleStart,
  cycleEnd)`が算出する「その周期の投稿数（実績＋予測の合算）」を、StripeのPrice tiers
  （`computeGraduatedAmount`、単価・閾値はハードコードせずStripeから都度取得）に
  当てはめて算出する

### レスポンス形式

```json
{
  "basicFee": 1480,
  "basicFeePeriod": { "year": 2026, "month": 9 },
  "usageFee": 840,
  "xSurcharge": 224,
  "total": 2544,
  "periodStart": "2026-08-25T02:15:04.000Z",
  "periodEnd": "2026-09-25T02:15:04.000Z",
  "isEstimate": true
}
```

- `periodStart`/`periodEnd`（前回決算日／次回決算日）はウィジェットのタイトル
  `ご請求予測（<periodStart>〜<periodEnd>）`、および従量料金・Xサーチャージ各行の
  期間付記（`yyyy年mm月dd日〜yyyy年mm月dd日`）に使う
- `basicFeePeriod`（次回決算日が属する年月）は基本料金の行の付記（`yyyy年mm月分`）専用。
  基本料金は先払い（決済日にその日から始まる次周期分を課金）のため、従量料金・
  Xサーチャージの期間表記（前回決算日〜次回決算日）とは粒度が異なる。フロント側で
  混同されないよう、行ごとに異なる形式のラベルを明示している（ユーザー要件）
- `cycleStart`が無い（本稼働前）場合、`periodStart`は`null`、`usageFee`/`xSurcharge`は0

### 投稿数の合算方式（`getCombinedPostCounts`、投稿実績ウィジェットとは別集計）

「予測投稿数 = 実績投稿数（前回決算日〜今日）＋ 予定投稿数（今日〜次回決算日、現在の
スケジュール設定が続いた場合）」という1本の式に統一している（ユーザー要件）。実額を
Stripeの`invoices.createPreview`からそのまま取るだけの旧実装（〜2026-08-25）は、
段階制tiersの閾値をまたぐ計算を正しく行うため廃止し、実績・予定とも「金額」ではなく
「件数」の時点で合算してからtiersに当てはめる方式にした。

- **実績（`postingLogStore.getActualPostCounts`）**: 周期開始日〜今日（`min(now, cycleEnd)`）
  の`posting_logs`（実行済みステータスの投稿）を実際の投稿日時（`posted_at`）で範囲集計する
- **予定（今日〜決済日）**: 「現在のスケジュール設定が続いた場合」の見積もりを2種類合算
  （未実行かつスケジュール設定済みの投稿のみが対象。実行済みは実績側でのみ計上するため
  二重計上しない）
  - 単発予約（`scheduledPostStore.getScheduledPostsSummary`。status=pendingの
    `scheduled_posts`を対象期間で範囲集計。旧実装は歴月単位だったが、任意の日時範囲を
    受け取れるよう改修した）
  - 繰り返しスケジュール（`getScheduleForecastForCustomer`→`estimateScheduleFirings`の
    シミュレーション。プラットフォーム別内訳counts・xUrlCount・totalCountを返すよう
    拡張した。post_schedulesの実データは書き換えない）
- 周期がまるごと未来（`cycleStart > now`）なら実績部分は自動的に空、まるごと過去
  （`cycleEnd <= now`。通常は起こらない）なら予定部分は自動的に空になる
- **Xサーチャージの対象は「URLリンク付きのX投稿」のみ**。全プラットフォーム合算の
  `totalCount`（従量料金の算出に使う）とは別に、X投稿かつURLリンク付きのものだけを
  `xUrlCount`としてカウントする（`mergeCounts`が実績・単発予約・繰り返しスケジュールの
  3つの内訳を`counts`（プラットフォーム別）・`xUrlCount`・`totalCount`のそれぞれで
  合算する）

「投稿実績」ウィジェットの実績集計（`getActualPostCounts`単体呼び出し）と、「ご請求予測」の
実績＋予定の合算（`getCombinedPostCounts`）は、いずれも同じ`getActualPostCounts`関数を
実績部分の唯一の実装として共有しており、実績集計ロジックの重複定義は無い。

## エッジケース・注意点

- 投稿実績・ご請求予測のいずれも、API失敗時はフロント側で「－」を表示するのみで
  エラーバナー等は出さない設計（ウィジェット単位で独立してサイレントフェイルする方針）
- SNS連携状況・Xサーチャージ情報も同様に、取得失敗を握りつぶして他機能に影響させない
  設計が随所に採用されている（コード内コメントで繰り返し明記されているパターン）
- 本ダッシュボードは正確な請求額の確定表示ではなく、あくまで概算の目安として提供する。
  実績・予定の境界（当日実行済みか未実行か等）について厳密なリアルタイム整合性までは
  求めない設計（ユーザー要件として明示）
