最終更新日: 2026-08-25（更新: trialPostLimitReachedフィールドを追加）
コード参照: sns-poster/src/routes/posts.js（stats/scheduled）,

## GET /api/auth/me が返す主なフィールド（ダッシュボードでの用途）

```
email, contactName, plan, isVerified, trialEndsAt, trialDisplayEndsAt, status,
trialPostLimitReached, coins, nextBillingDate, connectedPlatforms, user: { email, role }
```
`plan`はサインアップ機能で解説の`safeCustomer()`が生成。`user.role`はロール別ナビ挿入・
プロフィールメニューの解約ボタン表示判定に使用。`trialPostLimitReached`（2026-08-25
追加）はトライアル投稿上限到達バナー表示判定用（外部仕様・内部仕様_無料で始める
（トライアル）.md参照）。

## GET /api/posts/stats（投稿実績ウィジェット）

- `requireAuth`のみ（読み取り専用のため`requireVerified`等のガード無し）
- クエリ`year`,`month`（整数、month 1-12）不正なら400 `invalid_year_month`
- `postingLogStore.getPostStatsForCustomer(customerId, year, month)`:
  - `billingPeriod = "YYYY-MM"`文字列で`posting_logs`を`customer_code[equals]X[and]
    billing_period[equals]YYYY-MM`フィルタ
  - プラットフォーム別件数を集計（`billing_period`は投稿記録時に刻印された文字列であり、
    トライアルサイクル等とは独立した単純な暦月集計）
- レスポンスは`{x,threads,facebook,instagram}`をラップせずそのまま返す

## GET /api/posts/scheduled（投稿予定ウィジェット）

- `requireAuth`のみ
- `month`パラメータは`YYYY-MM`形式必須（400 `invalid_month`）、過去月は400 `month_in_past`
- `scheduledPostStore.getScheduledPostsSummary(customerId, year, month)`:
  - `status[contains]pending`（selectフィールドのため`[equals]`は常に0件になる、と
    コード内コメントに明記）かつ`scheduled_at`が該当月内のレコードを集計
- レスポンスは`summary.counts`のみ（`xUrlCount`・`totalCount`は算出されるがこの
  エンドポイントのレスポンスには含まれない）

## GET /api/billing/upcoming（ご請求予測ウィジェット、2026-08-26設計変更）

`month`パラメータの検証は上記と同一。Stripe未設定なら500 `stripe_not_configured`、
プラン価格未設定なら500 `plan_not_configured`。

### 「月」の基準はカレンダー月ではなくStripeの実請求サイクル

`estimateBillingForecast`（[billing.js](../src/routes/billing.js)）は、`month`パラメータ
（カレンダー年月）を「その月に決済日（Stripeが実際に請求を確定するタイミング）が来る周期」
に対応させて計算する。カレンダー月そのもので集計する旧実装（`predictFromScheduledPosts`・
`tryUpcomingInvoiceAmounts`、〜2026-08-25）は廃止した。

- **アンカー（基準時刻）**: `getBillingCycleAnchor`が、既にStripeサブスクリプションが
  存在する顧客は実際の`subscription.billing_cycle_anchor`を取得して使う。
  `customer.trialEndsAt`は決済登録後もクリアされず残り続ける内部値であり、実際の
  請求サイクルとズレていた実例が見つかったため、本稼働済みの顧客には使わない
  （実機で確認、2026-08-26）。まだCheckout未完了（トライアル中）の顧客のみ、
  `trialEndsAt + 1日`を将来のアンカー予測値として使う。
- **周期の進め方**: `addStripeStyleMonths(anchor, n)`が、Stripeの実際の月次課金アンカーの
  挙動（日単位・当月に該当日が無ければその月の最終日に丸める。例: 起点1/31なら2月は2/28、
  3月は3/31）を再現する。「歴月30日固定」でも「存在しない日は翌日に繰り越す」でもなく、
  **実際のStripeの挙動に合わせる**方針（要件定義時にユーザーが明示的に選択）。
- **周期番号n**: `findCycleIndexForMonth`が、対象カレンダー年月に決済日が属する周期番号n
  を求める（n=0が最初の決済＝本稼働開始日）。月次サイクルのため該当月には必ずちょうど1つ
  決済日が存在する。

### 先払い（基本料金）・後払い（従量料金・Xサーチャージ）

- **n<0**（本稼働前）: 全項目0円
- **n=0**（最初の決済月）: 基本料金のみ（従量分の対象期間がまだ存在しないため）
- **n≧1**: 基本料金＝この決済日から始まる次周期分（先払い）。従量料金・Xサーチャージ＝
  直前の決済日からこの決済日までに発生した投稿分（後払い）
  - 直近（Stripeが現在追跡している次回請求）の周期であれば、`fetchRealCycleUsage`が
    `stripe.invoices.createPreview`の実データをそのまま使う。**Stripeは実際に報告済みの
    Meterイベント（＝実投稿）を段階制課金込みでリアルタイムに反映しているため**
    （実機検証済み）、`posting_logs`を独自に再集計する必要はない。計算した決済日と
    `preview.period_end`が一致する場合のみ「実データ」として採用し、一致しなければ
    （＝Stripeがまだ追跡していない先の周期）nullを返してフォールバックする
  - 2周期以上先（Stripe側にまだ実績が無い月）は、`scheduled_posts`（単発予約）＋
    `post_schedules`の生成予定件数を、StripeのPrice tiers（`computeGraduatedAmount`、
    単価・閾値はハードコードせずStripeから都度取得）に当てはめて見積もる。単発予約の
    集計（`getScheduledPostsSummary`）は暦月単位のAPIのため、周期開始日が属する暦月で
    近似する（数ヶ月先の見積もりのため許容）

いずれも`{basicFee, usageFee, xSurcharge, total, isEstimate: true}`形式で返す。

## GET /api/billing/x-surcharge（Xサーチャージ情報カード）

認証不要の公開エンドポイント。`config/surcharge.json`の内容をそのまま返す。

## GET /api/sns-connections（SNS連携状況）

`requireAuth`のみ。詳細は内部仕様_SNS連携.md参照。フロント側コメントには「連携数・
上限判定はサーバーの応答を必ず信頼し、フロント側で独自に計算し直さない」という方針が
明記されている。

## 外部SaaS連携

Stripe（請求予測のみ、`stripe.invoices.createPreview`・`stripe.prices.retrieve`）

## microCMSスキーマへのI/O

読み取りのみ: `posting_logs`（billing_period, platform）, `scheduled_posts`
（status, scheduled_at, customer_code）, `post_schedules`（請求予測のスケジュール分）

  への重複実装のため、今後ナビ項目を変更する際は該当ページ全てへの反映漏れに注意）
- 実装: 左上固定の`#sidebar-toggle`（`.sidebar-toggle`、ハンバーガーアイコン）を押すと
  `#app-sidebar`（`.sidebar`）に`sidebar-open`クラスを付与して`translateX(-100%)`→
  `translateX(0)`でオフキャンバス表示。半透明の`#sidebar-backdrop`

  リンククリックで自動的に閉じる（`closeSidebar()`）。ブレークポイントは公開ページ側と
  同じ`max-width: 1024px`

## エッジケース・注意点

- 投稿実績・投稿予定・請求予測のいずれも、API失敗時はフロント側で「－」を表示するのみで
  エラーバナー等は出さない設計（ウィジェット単位で独立してサイレントフェイルする方針）
- SNS連携状況・Xサーチャージ情報も同様に、取得失敗を握りつぶして他機能に影響させない
  設計が随所に採用されている（コード内コメントで繰り返し明記されているパターン）
