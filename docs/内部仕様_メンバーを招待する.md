## 定数

```js
VALID_ROLES = ["管理者", "承認者", "編集者", "閲覧者"]
INVITATION_TTL_MS = 7日間
BCRYPT_ROUNDS = 12
```
メール形式・パスワード要件はauth.jsと同一基準（サインアップ参照）。

## APIエンドポイント一覧

| メソッド | パス | 認証 | 概要 |
|---|---|---|---|
| POST | /api/team/invite | requireAuth, requireVerified（管理者ロール限定） | メンバー招待 |
| GET | /api/team/members | requireAuth（ロール制限なし） | メンバー一覧取得 |
| DELETE | /api/team/members/:email | requireAuth（管理者ロール限定） | メンバー削除 |
| GET | /api/team/invite-info | 不要（トークン） | 招待トークンの事前確認 |
| POST | /api/team/accept-invitation | 不要（トークン） | 招待承諾・パスワード設定 |

## POST /api/team/invite

1. `currentUserRole(req.user) !== "管理者"` → 403 `forbidden`
2. バリデーション順: メール形式（400 `invalid_email`）→ 氏名必須（400 `invalid_name`）
   → 役割がVALID_ROLESに含まれるか（400 `invalid_role`）→ 役割が「編集者」の場合のみ、
   `approverIds`が空でないか（400 `approver_required`）・全IDが
   `validApproverCandidateIds(customer)`に含まれるか（400 `invalid_approver`）
3. `validApproverCandidateIds`: `invitationStatusOf(u) === "承諾済み"` かつ
   `role`が「管理者」または「承認者」のメンバーのみが承認者候補になれる
   （辞めたメンバーや別の編集者を承認者に指定できてしまうのを防ぐ、とコメントに明記）
4. 既存ユーザー（同一メール、小文字比較）が既に「承諾済み」なら409 `already_member`
5. **プラン別ユーザー数上限チェック（2026-08-22実装）**: 既存ユーザーが見つからない
   （＝`addInvitedUser`で`users`配列に新規要素を追加することになる）場合のみ実施。
   `getMaxTeamMembers(planKey(req.customer))`（`config/teamMemberLimits.json`:
   `basic:1, standard:3, advanced:3`）と`req.customer.users.length`を比較し、
   `currentCount >= maxMembers`なら403 `member_limit_reached`（レスポンスに`max`を
   含める）。既存のpending招待を`reissueInvitation`で上書きする場合は配列長が
   増えないためこのチェックはスキップする。**それまでは本チェック自体が存在せず、
   pricing.html記載の上限（Basic1/Standard・Advanced3）を超えて無制限に招待できて
   しまっていた**
6. 既存の未承諾（pending）招待があれば`reissueInvitation`で**同一users要素を上書き**
   （トークン・役割・承認者を再発行。配列に重複要素を追加しない）。無ければ
   `addInvitedUser`で新規要素を追加
7. `INVITATION_EMAIL`を送信（**送信失敗してもAPIは200 `{ok:true}`を返す**。非致命的エラー
   としてwarnログのみ）

## GET /api/team/members

- ロール不問で閲覧可能（承認者選択のため編集者自身も一覧を見る必要がある、とコメントに明記）
- レスポンス: `{ members: [{ userId, name, email, role, status, isOwner }] }`
- `isOwner`: `users`配列の**先頭要素かどうか**で判定。サインアップ時に作られる唯一の
  初期要素が常に先頭、以降の招待は必ず末尾に追加されるため先頭＝作成者であることが
  保証される（誤操作防止のための削除ボタン非表示判定に使われる）

## DELETE /api/team/members/:email

1. 管理者ロール以外は403 `forbidden`
2. `customerStore.removeMember`実行。`owner_cannot_be_removed`なら403、
   `member_not_found`なら404

## GET /api/team/invite-info（公開）

- トークン欠如: 400 `missing_token`
- `findCustomerAndUserByInvitationToken`で不一致: 404 `invalid_token`
- `invitationExpiresAt`（7日間）経過: 410 `expired_token`
- 既に「承諾済み」: 409 `already_accepted`
- 成功: `{ ok:true, email, role, companyName }`

## POST /api/team/accept-invitation（公開）

1. トークン欠如: 400 `missing_token`、パスワード要件未達: 400 `invalid_password`
2. `findCustomerAndUserByInvitationToken`で検索、期限確認、承諾済みチェック
   （invite-infoと同一ロジック）
3. bcryptでハッシュ化し`customerStore.acceptInvitation`実行（レース条件でトークンが
   消えていた場合はnullが返り404 `invalid_token`）
4. 成功時、**その場でJWTセッションを発行しCookieにセット**（承諾と同時に自動ログイン）

## accept-invitation.html のパスワード要件チェックリスト（2026-08-24変更、フロントのみ）

`password`inputの`input`イベントで`updatePasswordRequirements()`を呼び、4条件
（`/[A-Za-z]/`／`/[0-9]/`／`/[^A-Za-z0-9]/`／`length>=8`）それぞれの充足を判定して
該当`<li>`に`met`クラス（緑色）を付け外しし、テキスト先頭に「レ」を付け外しする。
change-password.html・パスワード再設定画面と同じ実装パターン（DOM構造・クラス名は
異なるが「満たすたびに緑チェックが増える」という挙動を踏襲）。**送信時のバリデーション
関数`isValidPassword()`自体は変更しておらず、この画面の要件セット（4項目、大文字小文字
区別なし）は従来のまま**。change-password.htmlは別途5項目（英大文字・小文字を別判定）
のバリデーション関数を持っており、要件セットの統一は行っていない（表示スタイルのみの
統一）。

## customerStore.js の主要関数

### `roleOf(user)` / `invitationStatusOf(user)`
microCMSのselectフィールド（配列格納）を単一値に正規化するヘルパー
（`Array.isArray(user.role) ? user.role[0] : user.role`）。

### `addInvitedUser(customerId, {...})`
`users`配列末尾に新要素を追加:
```js
{
  fieldId: "users", email, name,
  role: [role],
  approverIds: role === "編集者" ? JSON.stringify(approverIds||[]) : "",
  invitedBy: invitedByUserId,
  invitationToken, invitationExpiresAt,
  invitationStatus: ["招待中"],
}
```
この時点では`userId`・`passwordHash`は未設定（承諾時に初めて付与される）。

### `reissueInvitation(customerId, email, {...})`
既存のpending中招待（同一users要素）を、配列に追加せずその場で上書きする
（トークン・役割・承認者・招待日時を再発行＝実質的な再送信）。

### `acceptInvitation(customerId, invitationToken, passwordHash)`
トークン一致要素を以下で上書き:
```js
{ ...既存, userId: crypto.randomUUID(), passwordHash,
  invitationStatus: ["承諾済み"], invitationToken: "", invitationExpiresAt: "" }
```
`userId`が初めてここで割り当てられる。トークンはクリアされ再利用不可になる。

### `removeMember(customerId, email)`
- `index === -1`（該当なし）→ `{ok:false, error:"member_not_found"}`
- `index === 0`（作成者）→ `{ok:false, error:"owner_cannot_be_removed"}`
- それ以外は`users`配列から**要素ごと物理削除**（論理削除ではない）

## teamMemberLimitsConfig.js（getMaxTeamMembers）（2026-08-22新設）

```js
// config/teamMemberLimits.json
{ "basic": 1, "standard": 3, "advanced": 3 }
```
`planKey(customer)`（`stripePricing.js`。`basic`/`standard`/`advanced`に正規化）を
キーに上限人数を返す。SNS接続数の上限（`planLimitsConfig.js`・
`config/planLimits.json`）と同じ「JSONを都度読み込むだけの薄いラッパー」パターンを
踏襲している（キャッシュはしない）。

## セッションへの影響（削除時の仕組み）

`removeMember`はコメントで明記: 「users配列から該当要素を取り除くだけで、その場で
requireAuthの『該当userIdがcustomer.usersに存在しない』チェックに引っかかるようになり、
既存セッション（JWT）も含めて即座にアクセス不能になる（sessionVersion方式と同じく確実な
失効だが、要素自体が無くなるため個別のバージョン加算は不要）」。

`requireAuth.js`の実装（`const user = customer.users.find(u => u.userId === payload.userId); if (!user) return 401`）がこれを裏付ける。パスワード再設定等のsessionVersion方式とは異なる無効化手段。

## 外部SaaS連携

メール送信のみ（`INVITATION_EMAIL`テンプレート、customerMailer.js経由）。
件名「【EdgeAI Lab】メンバー招待のお知らせ」、本文に会社名（あれば）・承諾URL・
「このリンクの有効期限は7日間です。」を含む。

## microCMSスキーマへのI/O（customers.users[]）

読み書き: `email`, `name`, `role`, `approverIds`, `invitedBy`, `invitationToken`,
`invitationExpiresAt`, `invitationStatus`, `userId`, `passwordHash`

## エッジケース・注意点

- 招待メール送信が失敗してもAPIレスポンスは成功扱いになる（team.js/invite,
  approvalStore双方に共通するパターン）
- 「閲覧者」ロールに対する書き込み制限（`blockViewerRole`）は、本機能（team.js）の
  エンドポイントには適用されていないが、いずれも管理者ロール限定チェックが別途あるため
  実害はない
- ユーザー数上限チェックは`req.customer`（リクエスト時点のスナップショット）を使う
  ため、同時に複数の招待リクエストが飛んだ場合の厳密な排他制御はない（レース条件で
  上限を1名分超過する可能性は理論上ゼロではないが、招待は管理者による手動操作であり
  実運用上のリスクは低いと判断）
