# 内部仕様: ログイン

最終更新日: 2026-08-22
コード参照: sns-poster/src/routes/auth.js, sns-poster/src/lib/customerStore.js,
sns-poster/src/lib/jwt.js, sns-poster/src/middleware/requireAuth.js

## APIエンドポイント一覧

| メソッド | パス | 認証 | 概要 |
|---|---|---|---|
| POST | /api/auth/login | 不要 | メール・パスワードでログイン |
| POST | /api/auth/logout | 不要 | セッションCookie削除 |
| POST | /api/auth/request-password-reset | 不要 | パスワード再設定メール送信 |
| GET | /api/auth/password-reset-info | 不要（トークン） | 再設定トークンの有効性確認 |
| POST | /api/auth/reset-password | 不要（トークン） | 新パスワードの確定 |

## POST /api/auth/login

1. `customerStore.findCustomerAndUserByEmail(email)`で顧客・ユーザーを検索
   （本人のcustomers.emailだけでなく、招待メンバーのusers[].emailも横断的に検索する）
2. 見つからなければ401 `invalid_credentials`
3. `bcrypt.compare(password, user.passwordHash)`で照合。不一致なら401 `invalid_credentials`
   （「メール不存在」と「パスワード不一致」を区別しないメッセージ・ステータスコードにして
   列挙攻撃を防いでいる）
4. `signSession(customer, user)`でJWT発行、`setSessionCookie`でCookieセット
5. `{ ok: true, isVerified: customer.isVerified }`を返す

## POST /api/auth/logout

- `clearSessionCookie`でCookieを削除するのみ。サーバー側にセッションストアが無い
  （ステートレスJWT方式）ため、これ以外の処理は不要

## POST /api/auth/request-password-reset

- レート制限: メールアドレス単位（正規化: trim + 小文字化）で180秒
  （`PASSWORD_RESET_MIN_INTERVAL_MS`、インメモリMap）
  - 未登録メールアドレスであっても同じキーでレート制限を掛ける（429の発生有無自体が
    列挙攻撃の手がかりにならないようにする設計。コード内コメントに明記）
- `findCustomerAndUserByEmail`で対象を検索。見つかった場合のみ実際にトークン発行・メール送信
- 1時間有効（`PASSWORD_RESET_TOKEN_TTL_MS`）な`resetToken`を発行し、
  `customerStore.setPasswordResetToken(customerId, userId, token, expiresAt)`で
  該当users[]要素に記録（新しいトークンで上書きするため、過去の未使用トークンは
  自動的に無効化される）
- 見つかった・見つからなかったに関わらず、同一の成功レスポンス`{ok: true}`を返す

## GET /api/auth/password-reset-info

- `findCustomerAndUserByResetToken(token)`でトークン一致を検索。無ければ404 `invalid_token`
- `resetPasswordExpAt`（1時間）を経過していれば410 `expired_token`
- 有効なら`{ok: true}`のみ返す（実際のリセットはしない、参照専用）

## POST /api/auth/reset-password

1. トークン・新パスワード（要件チェック: 英大文字・英小文字・数字・記号各1文字以上、8文字以上）
   をサーバー側でも再検証
2. `findCustomerAndUserByResetToken`で対象確認、期限確認（password-reset-infoと同一ロジック）
3. `bcrypt.hash`で新パスワードをハッシュ化
4. `customerStore.resetPassword(customerId, token, passwordHash)`を実行。この関数は
   使用済みトークンをクリアし、**該当ユーザーのsessionVersionをインクリメント**することで
   発行済みの全セッション（他デバイス・他ブラウザ含む）を無効化する
5. 成功時`{ok: true}`（この時点では新セッションは発行されない。ユーザーは
   reset-password.html上の「ログイン画面へ」リンクから改めてログインする必要がある）

## セッション整合性チェック（requireAuth.js、ログイン後の全APIで共通）

`requireAuth`ミドルウェアは以下を検証する:
1. CookieからJWT取得・署名検証（`verifySession`）
2. `sub`（customer.id）に対応する顧客レコードが存在するか
3. `userId`に対応するユーザーがcustomer.users[]内に存在するか（削除済みメンバーの
   トークンはここで無効になる。外部仕様_メンバーを招待する.md参照）
4. JWTペイロードの`sessionVersion`が、現在のusers[].sessionVersionと一致するか
   （不一致ならパスワード再設定・変更・削除等で無効化された旧セッションと判断し401）

## 外部SaaS連携

なし（ログイン系機能自体は外部SaaS非依存。メール送信のみ`customerMailer.js`経由）

## microCMSスキーマへのI/O（customers）

読み取り: `email`, `users[].email/passwordHash/sessionVersion`
書き込み: `users[].resetPasswordToken/resetPasswordExpAt/passwordHash/sessionVersion`
（フィールド名は実装の`setPasswordResetToken`/`resetPassword`実装に準拠。要確認:
本ドキュメント作成時点でcustomerStore.js内のこれら関数のフィールド名詳細までは
逐語確認していないため、実装と齟齬があれば実装を正とすること）

## エッジケース・注意点

- レート制限（resend-verification・request-password-reset）はインメモリMapで実装されており、
  プロセス再起動でリセットされる。複数インスタンス構成では効かない（現行は単一コンテナ運用）
- パスワード再設定完了後は自動ログインされない設計（サインアップ直後の自動ログインとは
  意図的に挙動が異なる。コード上明示的な比較コメントは無いが、実装上の事実として記載）
