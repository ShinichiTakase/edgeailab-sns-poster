## 背景

メンバー招待機能（[内部仕様_メンバーを招待する.md](内部仕様_メンバーを招待する.md)）の
4ロール（管理者・承認者・編集者・閲覧者）のうち、サイドバーメニュー項目ごとの
使用可否を「閲覧者」（2026-08-27）・「編集者」（同日）の順に明文化・実装した。
承認者ロールについては本ドキュメント作成時点でメニュー制限の明文化された仕様は
まだ無く、既存実装のまま（team.html等は従来通りrole問わず閲覧可能）。

同日、「管理者に承認権限を持たせる」対応として、管理者にも「承認待ち一覧」
（approval.html）へのメニュー導線を追加した。承認バッチ（schedule_texts・
scheduled_postsのapproverIds）はロールではなくユーザー個人への紐付けで
判定する設計（`sns-poster/src/routes/approvals.js`、元々role不問）だったため、
サーバー側の変更は不要で、フロントのメニュー表示を広げるだけで機能した
（実際に管理者が承認候補として選べるようになった経緯は
[内部仕様_メンバーを招待する.md](内部仕様_メンバーを招待する.md)参照）。

## メニュー項目ごとの使用可否（仕様）

### 閲覧者

| メニュー項目 | 使用可否 | 内容 |
|---|---|---|
| ダッシュボード | 使用可 | 制限なし |
| SNS連携 | 制限付き使用可 | 連携状況の表示のみ。連携・削除は使用不可 |
| スケジュール投稿 | 使用不可 | メニュー非表示＋ページ自体アクセス不可 |
| ワンショット投稿 | 使用不可 | メニュー非表示＋ページ自体アクセス不可 |
| 投稿一覧 | 使用可 | 制限なし |
| メンバーを招待する | 制限付き使用可 | 一覧の表示のみ。招待は使用不可 |
| 請求情報 | 使用可 | 制限なし |
| お支払い方法 | 制限付き使用可 | カード情報の表示のみ。追加／削除／プライマリ・バックアップ入替は使用不可 |
| FAQ | 使用可 | 制限なし |
| アップグレード | 使用不可 | メニュー非表示＋ページ自体アクセス不可 |
| ログアウト | 使用可 | 制限なし |
| プロフィール | 制限付き使用可 | 解約のみ使用不可（従来からの実装） |

### 編集者（2026-08-27追加）

| メニュー項目 | 使用可否 | 内容 |
|---|---|---|
| ダッシュボード | 使用可 | 制限なし |
| SNS連携 | 使用不可 | メニュー非表示＋ページ自体アクセス不可（閲覧者と異なり表示すら不可） |
| スケジュール投稿 | 使用可 | 制限なし |
| ワンショット投稿 | 使用可 | 制限なし |
| 投稿一覧 | 使用不可 | メニュー非表示＋ページ自体アクセス不可 |
| メンバーを招待する | 使用不可 | メニュー非表示＋ページ自体アクセス不可（閲覧者は表示のみ許可だが編集者は表示も不可） |
| 請求情報 | 使用不可 | メニュー非表示＋ページ自体アクセス不可 |
| お支払い方法 | 使用不可 | メニュー非表示（ページ自体は既存の管理者/閲覧者限定ガードで従来から遮断済み） |
| FAQ | 使用可 | 制限なし |
| アップグレード | 使用不可 | メニュー非表示＋ページ自体アクセス不可（閲覧者と共通の仕組み） |
| ログアウト | 使用可 | 制限なし |
| プロフィール | 制限付き使用可 | 解約のみ使用不可（従来からの実装、閲覧者と共通） |

閲覧者と編集者で「使用不可」の中身が異なる点に注意: 閲覧者のSNS連携・
メンバーを招待するは「表示のみ許可（制限付き使用可）」だが、編集者はどちらも
「表示すら不可（使用不可）」。同じ「メニュー項目名」でもロールによって
許可レベルの意味が異なりうるため、実装時は都度この表を参照すること。

## 実装方針（フロント＋サーバーの二重防御）

各制限は基本的に「フロント側でUIを隠す／リダイレクトする」＋「サーバー側APIでも
同じロールチェックを行う」の二重構成にしている。フロント側の制御はURLを直接
知っている場合や開発者ツールでのDOM改変では防げないため、フロント側の対応
だけをセキュリティ境界として扱わないこと。

### サイドバー非表示（`js/role-nav.js`）

`insertRoleNavItems(role)`内の`ROLE_HIDDEN_NAV_HREFS`（ロール→非表示にする
`.sidebar-nav`内`href`の配列）と`ROLE_HIDDEN_UPGRADE`（アップグレードリンクを
非表示にするロールの配列）をテーブル参照する設計。新しいロール・項目を
追加する場合はこの2つの定数を編集するだけでよい。

```js
const ROLE_HIDDEN_NAV_HREFS = {
  閲覧者: ["schedule-list.html", "one-shot-post.html"],
  編集者: ["onboarding.html", "post-list.html", "team.html", "billing-history.html", "payment.html"],
};
const ROLE_HIDDEN_UPGRADE = ["閲覧者", "編集者"];
const ROLES_WITH_APPROVAL_QUEUE = ["管理者", "承認者"];
```

「承認待ち一覧」（approval.html）は`ROLES_WITH_APPROVAL_QUEUE`に含まれる
ロールに対し、`.sidebar-nav`内`a[href="post-list.html"]`の直後
（`insertAdjacentElement("afterend", ...)`）に挿入する。編集者向けの
「承認依頼一覧」（my-requests.html）は従来通り`a[href="team.html"]`の直前
（team.html自体が編集者には非表示のため、実際にはnullフォールバックで
末尾追加になる）。この2つは挿入位置のロジックが異なるため、
`insertRoleNavItems`内で別々のブロックとして扱っている（2026-08-27、
どちらも同じ`anchorLink`ロジックを共有する実装から分離した）。

### ページ直アクセス対策（`js/role-nav.js`の`redirectIfRoleForbidden`）

2026-08-27の閲覧者対応時点では`redirectIfViewerForbidden(role)`という
閲覧者専用の固定関数だったが、編集者対応にあわせて汎用化した:

```js
function redirectIfRoleForbidden(role, forbiddenRoles) {
  if (forbiddenRoles.includes(role)) {
    location.href = "dashboard.html";
    return true;
  }
  return false;
}
```

各ページの`init()`内、`/api/auth/me`取得直後・他の初期化処理より前に
`if (redirectIfRoleForbidden(me.user.role, [...])) return;`の形で呼ぶ。
呼び出し側の`forbiddenRoles`引数:

| ページ | forbiddenRoles |
|---|---|
| schedule-list.html / schedule-form.html / schedule-detail.html / one-shot-post.html | `["閲覧者"]` |
| onboarding.html / post-list.html / team.html / billing-history.html | `["編集者"]` |
| change-plan.html | `["閲覧者", "編集者"]` |

onboarding.htmlは元々サイドバーを持たない単体ページ（`insertRoleNavItems`を
呼んでいない）だが、`redirectIfRoleForbidden`だけは利用するため
`js/role-nav.js`の読み込みを新規に追加した（同様にchange-plan.htmlも
閲覧者対応時に読み込みを追加済み）。

### サーバー側ミドルウェア（`requireAuth.js`）

| ミドルウェア | 対象ロール | レスポンス | 用途 |
|---|---|---|---|
| `blockViewerRole` | 閲覧者 | JSON 403 | fetch系の書き込みAPI |
| `blockViewerRoleRedirect` | 閲覧者 | `/onboarding.html`へredirect | ブラウザ直接ナビゲーションのGETルート（SNS oauth start） |
| `blockEditorRole` | 編集者 | JSON 403 | fetch系のAPI（読み取り専用ルートにも使用） |
| `blockEditorRoleRedirect` | 編集者 | `/dashboard.html`へredirect | ブラウザ直接ナビゲーションのGETルート（SNS oauth start） |

閲覧者向けのredirect先は`/onboarding.html`（閲覧者にとってSNS連携は
「表示のみ許可」のため、連携できない旨をそこで見せる）、編集者向けのredirect先は
`/dashboard.html`（編集者にとってSNS連携はページごと使用不可のため、
onboarding.htmlへ戻しても仕方がない）という違いがある点に注意。

サーバー側の変更箇所（編集者、2026-08-27）:

- `snsConnections.js`: `POST /api/sns-connections/:platform/disconnect`に
  `blockEditorRole`を追加（既存の`blockViewerRole`と併用）。
- `instagram.js`・`threads.js`・`facebook.js`・`x.js`・`linkedin.js`:
  `/oauth/{platform}/start`に`blockEditorRoleRedirect`を追加（既存の
  `blockViewerRoleRedirect`と併用）。
- `posts.js`: `GET /api/posts/list`に`blockEditorRole`を追加。
  `GET /api/posts/stats`・`GET /api/posts/scheduled`（dashboard.htmlの
  投稿実績・投稿予定ウィジェットが使用、編集者にも使用可）は対象外。
- `team.js`: `GET /api/team/members`に`blockEditorRole`を追加。従来は
  「role問わず閲覧可能（承認者選択のため編集者自身も一覧を見られる必要が
  ある）」という設計コメントがあったが、実際に編集者向けページ（schedule-form.html
  等）がこのエンドポイントを呼んでいないことを確認したうえで、
  「メンバーを招待する：使用不可」の明文化された仕様を優先して遮断した。
- `invoices.js`: `GET /api/billing/invoices`・
  `GET /api/billing/invoices/:invoiceId/receipt`に`blockEditorRole`を追加。
- `billing.js`: `POST /api/billing/change-plan`に`blockEditorRole`を追加
  （既存の`blockViewerRole`と併用）。
- お支払い方法（`GET/POST /api/billing/payment-methods`系）は変更不要。
  既存の`requireAdminRole`（管理者限定）・`requireAdminOrViewerRole`
  （管理者・閲覧者限定、閲覧者対応時に新設）がどちらも編集者を除外して
  いるため、元々ブロックされていた。

### 「制限付き使用可」項目（閲覧者のみ、2026-08-27時点）

#### SNS連携（onboarding.html・dashboard.htmlのSNSアイコン）

- フロント: `onboarding.html`の`renderRow()`が`isViewer`のとき「連携する」
  リンクの代わりに非活性表示（`.platform-connect.is-disabled`）を出し、
  「削除」ボタン（`.platform-delete-link`）を出さない。`dashboard.html`の
  SNS連携状況アイコン（`loadSnsStatus()`）も同様に、閲覧者・編集者いずれにも
  削除ボタン（`.sns-icon-delete`）を出さない
  （`["閲覧者","編集者"].includes(currentMe.user.role)`で判定）。
- `GET /api/sns-connections`（連携状況の閲覧）はロール不問のまま
  （閲覧者・編集者とも、他の許可された画面がこのエンドポイントに依存しているため
  ブロックできない。詳細はコード参照のコメント）。

#### メンバーを招待する（team.html、閲覧者向け）

既存実装が招待ボタン（`#invite-open-btn`）をrole !== "管理者"で既に非表示化
しており、`POST /api/team/invite`もサーバー側で管理者ロール限定チェック
（`currentUserRole(req.user) !== "管理者"` → 403 forbidden）を持っていたため、
閲覧者対応時に変更した箇所は無い（閲覧者はこの既存の「管理者以外禁止」に
自動的に含まれ、一覧の閲覧だけができる）。編集者は前述の通りページ自体が
使用不可のため、この「表示のみ許可」の対象外。

#### お支払い方法（payment.html、閲覧者向け）

- 従来は「管理者以外はセクション自体を非表示にしてreturnする」実装
  （`me.user.role !== "管理者"`）だったため、閲覧者も含め全非管理者ロールが
  ページを一切閲覧できなかった。これを「管理者・閲覧者以外は非表示」に変更し、
  閲覧者の場合はカード一覧の取得（`loadCardList()`）のみ行い、カード追加ボタン
  （`#add-card-btn`）を非表示、`renderCardRow()`の削除ボタンを省略、
  `renderCardList()`のプライマリ／バックアップ入替行（`#swap-row`）を常に
  非表示にする。Stripe.js（`ensureStripeJs()`）は閲覧者パスでは一切呼ばれない
  （追加フォームを開くイベントリスナー自体を登録しないため）。
  承認者・編集者は従来通りページ非表示のまま。
- サーバー: `GET /api/billing/payment-methods`の権限チェックを、
  管理者限定の`requireAdminRole()`から、管理者・閲覧者を許可する新設の
  `requireAdminOrViewerRole()`に変更。カード追加（setup-intent・confirm）・
  削除・入替の4ルートは、元々`requireAdminRole()`（管理者以外を一律拒否）が
  かかっており、これが閲覧者・編集者含めて既にブロックしていたため
  変更不要と判断した。

## エッジケース・注意点

- `redirectIfRoleForbidden`・`insertRoleNavItems`のnav非表示は、あくまで
  UI上の導線を隠すためのものであり、単体ではセキュリティ境界にならない
  （ブラウザの開発者ツールでDOM操作すれば見た目上は再表示できる）。
  実際の防御は必ずサーバー側の`blockViewerRole`/`blockEditorRole`系
  ミドルウェアが担う。
- `blockViewerRoleRedirect`・`blockEditorRoleRedirect`は「フルページ遷移で
  叩かれるGETルート」専用。fetchベースのAPIには`blockViewerRole`/
  `blockEditorRole`（JSON 403）を使うこと。混同すると、fetch側はJSONパース
  失敗、フルページ遷移側は生JSON画面表示という形でUXが壊れる。
- あるAPIエンドポイントを特定ロールから遮断する際は、そのURLを他の
  「使用可」なページも呼んでいないか必ず確認すること（例:
  `GET /api/posts/scheduled`はdashboard.htmlとpost-list.htmlの両方が
  使いそうに見えるが、実際はdashboard.htmlのみ。逆に`GET /api/posts/list`は
  post-list.html専用）。grepで呼び出し元HTMLを網羅的に洗い出してから
  ミドルウェアを追加すること。
- 編集者ロールのテストアカウントが本番データに存在しなかったため、
  実装確認時は既存テスト用顧客レコード（biza3cp70）に一時的な編集者
  ユーザーを追加してAPIを直接検証し、確認後に削除して元に戻した
  （実運用データへの影響なし）。
