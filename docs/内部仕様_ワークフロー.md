# 内部仕様: ワークフロー（承認）

最終更新日: 2026-08-22
コード参照: sns-poster/src/routes/approvals.js, sns-poster/src/lib/approvalStore.js,
sns-poster/src/scripts/approvalExpiryCheck.js, sns-poster/src/lib/emailTemplates.js

## データモデル設計（重要な前提）

microCMSは無料プランのコンテンツタイプ5個上限に既に達しているため、承認者ごとの
レコードを独立コレクション（例: approvals）として新設せず、**対象レコード自体に
承認状態をJSON文字列で埋め込む**設計になっている（`approvals_json`）。1バッチは
複数レコードから成る（schedule_textsならAI一括生成のN件、scheduled_postsなら
投稿先プラットフォーム数件）ため、承認状態フィールド（`batch_id`/`approval_status`/
`appr_requested_at`/`appr_expires_at`/`approvals_json`）は**バッチ内の全レコードに
同一値を書き込んで揃える**（非正規化。5スキーマ制約下での妥協点、とコード冒頭コメントに
明記）。対象コレクションは`schedule_texts`と`scheduled_posts`の2種類。

## 定数

```js
APPROVAL_TTL_MS = 72 * 60 * 60 * 1000  // 72時間
```

## レコードあたりのフィールド（バッチ内全レコードで同一値）

- `batch_id`: `crypto.randomUUID()`
- `approval_status`（select配列）: `"pending" | "approved" | "rejected" | "expired" | "none"`
- `appr_requested_at`: ISO日時
- `appr_expires_at`: 依頼時刻+72時間
- `approvals_json`: 承認者ごとの配列をJSON文字列化したもの:
  `[{ approverId, status: "pending"|"approved"|"rejected", token, tokenExpiresAt, respondedAt, comment }]`
  （各承認者のtokenは生成時刻を基準に72時間、実質同時刻に発行されるため足並みは揃う）

`buildApprovalFields(approverIds)`: 承認者ごとに個別のトークン
（`crypto.randomBytes(32).toString("hex")`）を生成し、上記フィールド一式を返す
（`approval_status: ["pending"]`）。

`noneApprovalFields()`: 管理者が直接作成した場合（承認不要）に使う。`batch_id: ""`、
`approval_status: ["none"]`、他の日時・JSON系フィールドは空。schedules.js側の
コメントによれば、これを明示的にセットしないと自動生成プールの絞り込み
（`approval_status[not_contains]pending/rejected/expired`）で意図しない挙動になるため
必須。

## APIエンドポイント一覧

| メソッド | パス | 認証 | 概要 |
|---|---|---|---|
| GET | /api/approvals/mine | requireAuth | 自分が承認者として紐付くpending中バッチ一覧 |
| GET | /api/approvals/requests | requireAuth | 自分が作成した依頼の全ステータス一覧 |
| GET | /api/approvals/by-token/:token | 不要 | メールリンク経由での単一バッチ取得 |
| POST | /api/approvals/decide | 任意（セッションorトークン） | 承認・却下の決定 |

### GET /api/approvals/mine

コメントに明記: 「role問わず、自分がpending中の承認者として紐付いているバッチを返す
（管理者が承認者に指定されているケースもあり得るため、roleでは絞らない）」。
`schedule_texts`・`scheduled_posts`両コレクションを横断して
`approvalStore.listPendingApprovalsForApprover(collection, userId)`を呼ぶ。

### GET /api/approvals/requests

自分（`req.user.userId`）が作成したバッチを全ステータス横断で取得
（`listBatchesByCreator`）。

### GET /api/approvals/by-token/:token（公開）

- トークン不一致: 404 `invalid_token`
- `status !== "pending"` または`appr_expires_at`経過: 410 `expired_or_decided`
- 同一承認者が紐付く他のpendingバッチも`otherBatches`として返すが、
  `includeApprovals: false`で承認者詳細は含めない（他バッチの中身は漏らさない）

### POST /api/approvals/decide

`requireAuth`は使わず、独自の`resolveOptionalSession(req)`でセッションが**あれば**
検証するが、無くてもエラーにしない（メール内トークンのみでのアクセスを許容するため）。
セッションもトークンも無ければ401 `unauthenticated`。

処理: `collection`が`["schedule_texts","scheduled_posts"]`に含まれるか（400
`invalid_collection`）、`decision`が`["approved","rejected"]`か（400 `invalid_decision`）
を検証後、`approvalStore.decideApproval(...)`を実行。

エラーマッピング: `not_found→404, already_decided→409, expired→410, not_approver→403,
already_responded→409`（他は400）。

**却下が確定した場合のみ**、依頼者（作成者）宛に`APPROVAL_DECIDED_EMAIL`
（`decision: "rejected"`）を送信する。承認（部分・全員確定いずれも）の場合は
メール送信されない。

## decideApproval のAND/OR判定ロジック（重要）

1. バッチの`status === "pending"`を確認（そうでなければ`already_decided`）、期限内か確認
   （超過していれば`expired`）
2. 呼び出し者自身の承認エントリを`approverId`またはトークンで特定。見つからなければ
   `not_approver`、既に`pending`以外なら`already_responded`
3. **却下の場合**: そのエントリのみ更新した上で、**即座にバッチ内の全レコードへ
   `approval_status: ["rejected"]`を書き込む**（他の承認者の判断を待たず、
   1人の却下で即バッチ全体が却下確定する＝OR的挙動）
4. **承認の場合**: `approvals_json`内の全承認者の`status`を確認し、
   `allApproved = 全員approved`なら`approval_status: ["approved"]`、
   そうでなければ`["pending"]`のまま（＝AND的挙動。1人の承認だけでは確定しない）

**結論**: 承認は全員一致（AND）が必要だが、却下は1人でも成立する（OR）という
非対称な設計。

## 承認期限切れバッチの処理（72時間タイムアウト）

`checkExpiredApprovals(collection, onExpired)`:
- `approval_status[contains]pending`の全レコードを取得し`batch_id`でグルーピング
- `appr_expires_at < now`のバッチのみ対象
- 各対象バッチについて、パッチ直前に改めて`status === "pending"`かを再確認
  （スキャンとパッチの間に決定が入るレース条件への防御）
- **`approval_status`フィールドのみを`["expired"]`に書き換える。`approvals_json`内の
  各承認者エントリは更新されず`pending`のまま残る**（要確認: バッチ全体のステータスは
  失効扱いになるが、個々の承認者のJSON内ステータス表示とは食い違う。過去データを見た際に
  混乱しないよう留意）
- `onExpired(batch)`コールバックで依頼者への失効通知メール送信をトリガー

## cron: approvalExpiryCheck.js

想定起動間隔: 15〜30分おき（コード内コメント）。`schedule_texts`・`scheduled_posts`
両方に対し`checkExpiredApprovals`を実行し、期限切れバッチを`expired`にマークしつつ
依頼者へ通知メールを送る。実際の予約投稿・スケジュールレコード自体には触れず、
このステータスフィールドの書き換えのみ行う。

**要確認**: CLAUDE.mdには他の同種cron（Instagram/Threadsリフレッシュ、コイン付与等）と
異なり、`approval-expiry-check`のcrontab登録例が明記されていない。ただし実際の
`/etc/cron.d/edgeailab-net-approval-expiry-check`には20分おきの登録が存在することを
別途確認済み（稼働中）。

## 自動投稿プールへの影響（他機能との接続点）

`scheduleTextStore.js`・`scheduledPostStore.js`双方の自動生成/実行対象フィルタに
以下3条件が含まれる:
```
approval_status[not_contains]pending
approval_status[not_contains]rejected
approval_status[not_contains]expired
```
つまり自動投稿の対象になれるのは`approved`または`none`（承認不要＝管理者作成）の
レコードのみ。72時間タイムアウト（→expired）・却下（→rejected）のいずれも、
恒久的にそのレコードを投稿プールから除外する。再投稿するには編集者が新しいバッチを
作り直す必要がある。

## 権限体系（機能横断まとめ）

| ロール | 承認依頼を作成できるか | 承認者になれるか | 直接保存できるか |
|---|---|---|---|
| 管理者 | - | ○（承認者候補） | ○（承認不要） |
| 承認者 | - | ○ | - |
| 編集者 | ○（必須） | × | ×（必ず承認依頼経由） |
| 閲覧者 | × | × | × |

## 外部SaaS連携

メール送信のみ（`customerMailer.js`経由）。3種類のテンプレート:
- `APPROVAL_REQUEST_EMAIL`（依頼時、各承認者へ）
- `APPROVAL_DECIDED_EMAIL`（却下時・失効時、依頼者へ。承認時は送信されない）

## microCMSスキーマへのI/O

schedule_texts / scheduled_posts 共通: `batch_id`, `approval_status`,
`appr_requested_at`, `appr_expires_at`, `approvals_json`

## エッジケース・注意点

- 却下は1人でも即確定するが、承認は全員一致が必要という非対称設計
- 承認完了時のメール通知が存在しない（依頼者は一覧画面を能動的に確認する必要がある）
- 失効時、`approval_status`は書き換わるが`approvals_json`内の個別ステータスは
  更新されないままになる
