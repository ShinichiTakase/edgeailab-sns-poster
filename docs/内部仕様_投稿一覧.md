## GET /api/posts/list の集約ロジック

即時投稿（`posting_logs`）と予約投稿（`scheduled_posts`）を横断して顧客の全件を返す。

### posting_logs由来の行
- `isImmediate: !postingLogOriginStore.isFromScheduledPost(log.id)`（予約投稿が
  実行された結果のログを「即時」表示しないための判定）
- `result`は常に`"success"`（posting_logsは成功時にしか作られないため失敗は含まれない）
- `completedAt: log.posted_at || log.createdAt`

### scheduled_posts由来の行
- `status="done"`のものは**除外**（posting_logs側で既に記録済みのため重複行防止）
- **`approval_status="rejected"`（承認者が却下した投稿）は`result="rejected"`
  （2026-08-27追加）**。`approvalStore.decideApproval()`は却下時に`approval_status`
  のみを更新し、`status`フィールドは実行エンジン（`scheduledPostExecutor.js`）が
  投稿を試みて初めて変わる設計のため、却下された投稿の`status`は`pending`のまま
  永久に変化しない。この修正前は`status`だけを見ていたため、却下済み（二度と
  実行されない）投稿が一覧上いつまでも「予約中(pending)」と表示されてしまう
  不具合があった（実機で発覚: tester03@edgeailab.netが作成し却下された
  ワンショット投稿）。判定はこの`approval_status`チェックを`status="failed"`判定
  より先に行う
- `status="failed"`（かつ却下ではない）は`scheduledPostRetryStore.getDisplayState(post.id)`
  で「再試行(retrying)」か「失敗(failed)」かを判定
- `accountName`は常にnull（実行完了前のためアカウント未確定という設計判断がコメントに
  明記。**却下された投稿も同様に常にnullのまま**＝一覧の「アカウント」列が「-」に
  なるのは、その投稿がまだ実際にSNSへ投稿されていない〔pending/failed/retrying/
  rejectedのいずれか〕ことを意味する。実際に投稿済み〔posting_logs由来の行〕のみ
  アカウント名が確定して表示される）
- `postDateTime`は予約が**作成された**日時（実際の投稿日時は`completedAt`が担う、
  という役割分離がコメントで明記されている）
- `scheduledAt`は`result="pending"`のときのみセット（実行完了後・却下後はブランク。
  以前は`status="pending"`で判定していたが、却下時も`status`が変わらないため
  `result`基準に統一した）。`completedAt`はその逆（`result!=="pending"`のとき
  `post.updatedAt`をセット）。却下時の`completedAt`は承認バッチ内の正確な却下時刻
  （`approvals_json`内の`respondedAt`）ではなく、簡便のためレコード全体の
  `updatedAt`で代用している

全行を`postDateTime`降順にソートして返却。

レスポンス形状:
```
{ rows: [{ postDateTime, email, platform, accountName, content, scheduledAt,
           isImmediate, completedAt, result }] }
```
`result`の取りうる値: `success` / `failed` / `retrying` / `pending` / `rejected`
（フロント側`post-list.html`の`RESULT_LABELS`: 成功／失敗／再投稿／予約中／却下）。

## src/lib/postingLogStore.js

`posting_logs`はmicroCMSの`select`フィールド前提。

**`account_name`フィールドはmicroCMS側スキーマに手動追加が必要**であり、未対応環境
では書き込み時に400エラーになる。`createPostingLog()`はこの400を検知（レスポンス
テキストに`"account_name"`を含むか判定）した場合、`account_name`を除いたbodyで
**自動リトライ**する設計になっている（コメント: 「投稿ログの記録は投稿成否そのもの
より優先度が低いため、フィールド未対応が原因の場合はこのフィールドを落として再送し、
記録自体は失わないようにする」）。**現状（2026-08-22）は実装済み**（過去のmicroCMS
スキーマ未対応環境向けフォールバックコードだが、フォールバック自体は本番に残っている）。

`account_name`の値は`tokenStore.js`の`accountNameFor(platform, tokenEntry)`で
解決され、投稿時点で実際に紐づいていたSNSアカウント名を記録する。コメントに明記された
理由: 「連携し直したら別アカウントに投稿されていた」事故（2026-08-21、SNS連携機能の
内部仕様参照）の再発時に、どのアカウントに投稿されたかを事後追跡できるようにするため。

`getPostStatsForCustomer`: 月次のプラットフォーム別投稿件数集計（ダッシュボード用、
本画面自体では未使用）。

## src/lib/postingLogOriginStore.js

- ファイルベース（`json/posting_log_origins.json`）の暫定実装（`tokenStore.js`・
  `scheduledPostRetryStore.js`と同じ方針）
- `posting_logs`のmicroCMSスキーマには「予約投稿由来か」を示すフィールドが無く、
  追加には管理画面での手動スキーマ変更が必要なため、この軽量な補助データで代替している
  （コメントに明記）
- `recordScheduledOrigin(postingLogId, scheduledPostId)`: `scheduledPostExecutor.js`が
  投稿成功時に呼ぶ
- `isFromScheduledPost(postingLogId)`: 本APIが「予定日時＝即時」表示すべきでないかの
  判定に使う

## エッジケース・注意点

- `posting_logs`側の`account_name`フィールドは環境によってはmicroCMSスキーマ未対応の
  可能性が残っており、その場合はアカウント名が記録されずフォールバック動作となる
- ジョブ管理・投稿ログ記録がファイルベースの補助データに依存している箇所があり
  （`postingLogOriginStore.js`）、microCMSの無料プラン制約（コンテンツタイプ5個上限）
  が理由として明記されている
