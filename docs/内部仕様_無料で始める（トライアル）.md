## トライアル期間の内部値と表示値（重要・全機能横断で影響）

`customers.trialEndsAt`（microCMS上の実値）は、顧客に案内する「表向き30日」ではなく
**33日**（`TRIAL_DAYS`=30 + `TRIAL_INTERNAL_BUFFER_DAYS`=3）で設定される
（auth.js内定数）。

- 理由: Stripe Checkout SessionのsSubscriptionData.trial_endには「現在時刻より2日超先」
  必須という制約があり（実測確認済み）、表向き30日ぎりぎりに決済登録されるとこの制約に
  抵触し即時課金にフォールバックしてしまうため、常に3日超の余裕を内部的に確保している
- アクセス制御（`isTrialExpiredWithoutPayment`）・請求予測（billing.js）・トライアル終了
  リマインドcron・Stripe Checkoutのtrial_end設定は、この33日基準のtrialEndsAtをそのまま使う
- ダッシュボード等の「残り◯日」表示専用に、`GET /api/auth/me`が`trialDisplayEndsAt`
  （trialEndsAtから3日引いた「表向き」の終了日時）を別途返す。表示にはこちらを使うこと

## トライアル開始（サインアップ時）

`POST /api/auth/signup`（auth.js）内で以下を設定:
```
status: ["trial"]
trialEndsAt: now + 33日
```
customerStore.createCustomer が microCMS `customers` スキーマに書き込む。

再サインアップ（解約済み顧客が同一メールで登録し直す場合）は `reactivateCustomer` を使うが、
**2026-08-22の修正でトライアルは付与されなくなった**:
```
status: ["active"]   // "trial"にはしない
isVerified: false
trialEndsAt: ""       // 空にする（trialEndsAtパラメータ自体は無視する）
trialPostCount: 0
trialReminderSent: false
stripeSubscriptionId: ""
```

**経緯（要修正だった旧実装）**: reactivateCustomerを導入したコミット（`23bf48a`,
2026-08-16）のメッセージには「解約済みcustomerが同一メールで再サインアップした際、
重複エラーではなくreactivateCustomerで既存レコードを再アクティブ化するよう分岐
（**無料トライアルの再取得抜け穴を防止**）」と明記されていたにもかかわらず、実際の
実装は`status: ["trial"]`・新しい`trialEndsAt`（33日後）を設定しており、まさに
「抜け穴」そのものを再現していた（意図と実装が矛盾する実装漏れ。仕様書作成時の
レビューで発覚し2026-08-22に修正）。

customers.statusのselect選択肢はtrial/active/canceledの3つしか定義されておらず
（microCMS管理画面側の変更が必要でコードからは追加不可）、「トライアルなし・未払い」
専用の値は使えないため、既存の`"active"`を流用している。実際のアクセス制限は
`requiresPaymentRegistration()`（下記）が担う。

## トライアル中の投稿数上限

- `customerStore.TRIAL_POST_LIMIT = 60`
- `isTrialPostLimitReached(customer)`: `status === "trial" && trialPostCount >= 60`
- `requireUnderTrialPostLimit`ミドルウェア（requireAuth.js）で、投稿系エンドポイントに
  組み込まれている（即時投稿・予約投稿の両方）
- `trialPostCount`は`bumpTrialPostCount`で加算。ループ内で複数回呼ぶとreq.customerの
  古い値を基準に重複加算するバグになるため、呼び出し側は成功件数を集計してから
  一度だけ呼ぶ設計になっている（コード内コメントより）

## 支払い登録が必要かどうかの判定（2026-08-22改名・拡張）

`requiresPaymentRegistration(customer)`（customerStore.js、cron・requireAuth.js両方から
参照される純粋関数。旧名`isTrialExpiredWithoutPayment`）:
```js
if (customer.stripeSubscriptionId) return false;
const status = ...;
if (status === "canceled") return false;
if (status !== "trial") return true;          // reactivateCustomer後のstatus:"active"はここで即true
if (!customer.trialEndsAt) return false;
return new Date(customer.trialEndsAt).getTime() < Date.now();
```

判定対象が2種類に拡張されている:
- **トライアル中（status:"trial"）**: 従来通りtrialEndsAt（内部値・33日基準）を経過するまでは
  猶予する
- **トライアル以外・未払い（reactivateCustomer後のstatus:"active"）**: 猶予期間を設けず、
  stripeSubscriptionId未登録なら常に`true`。正規のStripe決済完了時は必ず
  stripeSubscriptionIdと同時にstatus:"active"がセットされるため、実際に課金済みの顧客が
  誤ってブロックされることはない

利用箇所:
- `blockExpiredTrial`ミドルウェア（requireAuth.js）: SNS連携開始（OAuth authorize系
  エンドポイント）・投稿系エンドポイント（`POST /api/posts`・`POST /api/posts/schedule`・
  `POST /api/schedules`・`PATCH /api/schedules/:id`等）の両方に組み込まれている。該当すると
  `status==="trial"`なら`/upgrade.html?reason=trial_expired`、それ以外（再登録後の
  未払い）なら`/upgrade.html?reason=payment_required`へリダイレクト（2026-08-22実機検証済み:
  解約→同一メール再登録後、メール認証済みの状態で`POST /api/schedules`・
  `GET /oauth/x/authorize`双方が`reason=payment_required`へ302リダイレクトされることを確認）
- `scheduleMaterializer.js`: 該当顧客のスケジュールは新規のscheduled_posts生成対象から除外
- `scheduleAutoPauseSync.js`（日次cron、稼働確認済み・`/etc/cron.d/edgeailab-net-schedule-auto-pause-sync`
  で毎日4時登録）: 該当顧客の全post_schedulesを`auto_paused: true`にし、未実行のpending
  scheduled_postsを取り消す。復帰時（支払い登録等でrequiresPaymentRegistrationがfalseに
  戻った場合）はauto_pausedをfalseに戻す（ユーザー自身によるis_pausedには一切触れない）

## トライアル終了リマインドメール

`src/scripts/trialReminderCheck.js`（単発実行スクリプト）:
- `customerStore.listCustomersWithUpcomingTrialEnd(3)`で、`isVerified: true` かつ
  `trialReminderSent: false` かつ `trialEndsAt`（内部値・33日基準）が3日以内の顧客を抽出
- 該当者にTRIAL_ENDING_EMAILを送信し、成功したら`trialReminderSent: true`を記録（1顧客1回のみ）
- コード内コメントにより、実際にメールが届くのは「表向きの終了日（trialEndsAt-3日）の
  当日〜3日後」の間になる（このREMINDER_WINDOW_DAYS=3と内部バッファ3日は別々の設定であり、
  たまたま同じ日数なだけで意図的に連動しているわけではないと明記されている）

**cron登録状況（2026-08-22修正済み）** — 仕様書作成時のレビューで、
`docker-compose.yml`にサービス定義自体が存在せず、`/etc/cron.d/`・root個人crontab
のいずれにも対応するcron登録が無いことが判明した（他の同種スクリプトは
`profiles: manual`サービス定義＋CLAUDE.mdへのcrontab登録例があったのに対し、
trialReminderCheck.jsだけが定義漏れだった）。おそらく本番で一度も実行されていなかった。

対応: `docker-compose.yml`に`sns-poster-trial-reminder-check`サービスを追加し、
`/etc/cron.d/edgeailab-net-trial-reminder-check`で**毎日5時**に実行するよう登録した
（`sns-poster-approval-expiry-check`と同一構成。customerMailer経由の送信のため
`network_mode: host`は不要）。ビルド・試験実行して稼働確認済み（本番唯一のトライアル
顧客は当時リマインド対象外の日数だったため、実際のメール送信は発生させていない）。

## 外部SaaS連携

- Stripe: このスクリプト自体はStripeを呼ばない。trial_end設定はサインアップ時ではなく、
  実際のCheckout Session作成時（billing.js、外部仕様_アップグレード.md側）に行われる
- メール送信: `customerMailer.js`経由（SMTP、`mail.edgeailab.net`宛の認証付き中継。
  障害通知専用の`mailer.js`＝ホストのpostfix 127.0.0.1:25宛とは別経路のため混同注意）
