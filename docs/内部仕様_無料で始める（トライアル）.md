## トライアル期間の内部値と表示値（重要・全機能横断で影響）

`customers.trialEndsAt`（microCMS上の実値）は、顧客に案内する「表向き30日」ではなく
**33日**（`TRIAL_DAYS`=30 + `TRIAL_INTERNAL_BUFFER_DAYS`=3）で設定される
（auth.js内定数）。

- 理由: Stripe Checkout SessionのsSubscriptionData.trial_endには「現在時刻より2日超先」
  必須という制約があり（実測確認済み）、表向き30日ぎりぎりに決済登録されるとこの制約に
  抵触し即時課金にフォールバックしてしまうため、常に3日超の余裕を内部的に確保している
- アクセス制御（`isTrialExpiredWithoutPayment`）・請求予測（billing.js）・トライアル終了
  リマインドcron・Stripe Checkoutのtrial_end設定は、この33日基準のtrialEndsAtをそのまま使う
- ダッシュボード等の「残り◯日」表示専用に、`GET /api/auth/me`が`trialDisplayEndsAt`
  （trialEndsAtから3日引いた「表向き」の終了日時）を別途返す。表示にはこちらを使うこと

## トライアル開始（サインアップ時）

`POST /api/auth/signup`（auth.js）内で以下を設定:
```
status: ["trial"]
trialEndsAt: now + 33日
```
customerStore.createCustomer が microCMS `customers` スキーマに書き込む。

再サインアップ（解約済み顧客が同一メールで登録し直す場合）は `reactivateCustomer` を使うが、
**2026-08-22の修正でトライアルは付与されなくなった**:
```
status: ["active"]   // "trial"にはしない
isVerified: false
trialEndsAt: ""       // 空にする（trialEndsAtパラメータ自体は無視する）
trialPostCount: 0
trialReminderSent: false
stripeSubscriptionId: ""
```

**経緯（要修正だった旧実装）**: reactivateCustomerを導入したコミット（`23bf48a`,
2026-08-16）のメッセージには「解約済みcustomerが同一メールで再サインアップした際、
重複エラーではなくreactivateCustomerで既存レコードを再アクティブ化するよう分岐
（**無料トライアルの再取得抜け穴を防止**）」と明記されていたにもかかわらず、実際の
実装は`status: ["trial"]`・新しい`trialEndsAt`（33日後）を設定しており、まさに
「抜け穴」そのものを再現していた（意図と実装が矛盾する実装漏れ。仕様書作成時の
レビューで発覚し2026-08-22に修正）。

customers.statusのselect選択肢はtrial/active/canceledの3つしか定義されておらず
（microCMS管理画面側の変更が必要でコードからは追加不可）、「トライアルなし・未払い」
専用の値は使えないため、既存の`"active"`を流用している。実際のアクセス制限は
`requiresPaymentRegistration()`（下記）が担う。

## トライアル中の投稿数上限

- `customerStore.TRIAL_POST_LIMIT = 60`
- `isTrialPostLimitReached(customer)`: `status === "trial" && trialPostCount >= 60`
- `requireUnderTrialPostLimit`ミドルウェア（requireAuth.js）で、投稿系エンドポイントに
  組み込まれている（`POST /api/posts`即時投稿・`POST /api/posts/schedule`ワンショット
  予約投稿の両方。文言は`` `トライアル中の投稿上限（${TRIAL_POST_LIMIT}通）に達しました` ``）
- `trialPostCount`は`bumpTrialPostCount`で加算。ループ内で複数回呼ぶとreq.customerの
  古い値を基準に重複加算するバグになるため、呼び出し側は成功件数を集計してから
  一度だけ呼ぶ設計になっている（コード内コメントより）

### 不具合: 継続スケジュール投稿（post_schedules）経由の投稿がtrialPostCountに
### 一切カウントされない（2026-08-25発見・修正）

`bumpTrialPostCount`の呼び出し箇所は修正前、`src/routes/posts.js`の2箇所
（即時投稿・ワンショット予約投稿の作成時）のみだった。一方、実際の投稿の大半を
占める**継続スケジュール（`post_schedules`→`scheduleMaterializer.js`が生成した
`scheduled_posts`を`scheduledPostExecutor.js`が実投稿する経路）は、生成時・実行時
のどちらでも`bumpTrialPostCount`を一度も呼んでいなかった**。

`scheduleMaterializer.js`・`scheduledPostExecutor.js`はどちらも`isTrialPostLimitReached`
を参照してブロック判定だけは行っていたため、一見「上限チェックが効いている」ように
見えるコードだったが、参照している`trialPostCount`自体が実態を反映しない値のまま
だったため、実質的にチェックが機能していなかった。

**実機での確認（2026-08-25、shin.takase@icloud.com、読み取りのみで確認）**:
`customers.trialPostCount`は34のままだったが、`posting_logs`の実件数は143件
（うち137件が継続スケジュール経由）。トライアル顧客が60通の上限を大幅に超えて
投稿し続けられる状態だった。

**修正**: `src/lib/scheduledPostExecutor.js`の`attemptScheduledPost`内、投稿成功
（`markScheduledPostStatus(post.id, "done")`直後）で、`post.source_schedule_id`が
ある場合（＝継続スケジュール由来）のみ`bumpTrialPostCount(customerCode, customer, 1)`
を呼ぶ。`source_schedule_id`が無い場合（ワンショット投稿ウィザードからの予約投稿）は
`posts.js`側で作成時に既に加算済みのため、ここでは呼ばない（二重加算防止）。

- 継続スケジュールは「予約作成」と「投稿確定」が分離しておらず（曜日・時間帯設定に
  基づきcronが動的に生成するため、作成時点で何通生成されるか未確定）、ワンショット
  予約投稿のような「作成時カウント」方式が使えない。実行成功時にカウントする以外の
  設計は無い
- `customerCache`（呼び出し元のcron scriptが同一実行内で使い回すMap）上の`customer`
  オブジェクトも`bumpTrialPostCount`の戻り値で更新する。これをしないと、同一cron
  実行内で同一顧客の複数投稿を処理する際、2件目以降が古い`trialPostCount`を基準に
  `isTrialPostLimitReached`判定してしまい、上限を超えて実行され続ける（`posts.js`の
  「ループ内で複数回呼ぶと重複加算バグになる」という既知の注意点の裏返しの問題。
  ただしこちらは「更新し忘れると加算漏れ判定になる」方向）
- カウント処理自体が失敗しても投稿の成否には影響させない（`try/catch`でログのみ。
  メーターイベント送信・投稿ログ記録と同じ既存パターンを踏襲）
- テスト: `src/lib/scheduledPostExecutor.test.js`（`node --test`。SNS投稿API・
  microCMSへの実アクセスは行わずすべてフェイクに差し替え。「継続スケジュール由来は
  加算される」「ワンショット予約由来は二重加算しない」「同一cron実行内の複数投稿が
  古い値を基準に重複加算/加算漏れしない」を検証）
- **未対応（データ修正）**: 上記の不具合により過去に実態より少なくカウントされて
  しまった既存トライアル顧客の`trialPostCount`（shin.takase@icloud.comを含む）は、
  本修正では遡って補正していない。修正後は新規の継続スケジュール投稿からのみ
  正しくカウントされる

## トライアル投稿上限到達バナー（2026-08-25追加）

`GET /api/auth/me`（`safeCustomer()`、`src/routes/auth.js`）に
`trialPostLimitReached: isTrialPostLimitReached(customer)`を追加した（それまでは
上限到達を示すフラグがレスポンスに一切含まれておらず、ダッシュボード側で
バナー表示を出す手段自体が無かった）。

- フロント側（`edgeailab.net/dashboard.html`）: `me.trialPostLimitReached === true`
  または`me.trialLimitAutoActivated === true`（後述「投稿上限到達時の自動アクティベート」
  参照。2026-08-25追加）のとき、既存の`trial-bar`（トライアル終了案内）と同じ
  実装パターンで新設の`.trial-limit-bar`を表示する。**この判定は`me.status==="trial"`
  の外側で行う**（自動アクティベートでstatusが"active"に変わった後もバナーを
  出し続ける必要があるため。2026-08-25変更、下記参照）
- 文言は`hasPaymentMethod`（`me.trialLimitAutoActivated`がtrueなら自動アクティベート
  時点で支払い方法登録済みと確定しているため問い合わせ不要でtrue扱い。それ以外は
  `GET /api/billing/payment-methods`のcards件数で判定。トライアル終了バーと同じ
  ロジックを共用）で出し分け:
  - 未登録: 「トライアル中の投稿上限（60通）に達しました。お支払方法を登録されると
    投稿が再開され、基本料金が発生し投稿は課金されます」＋「お支払い情報を登録する」
    リンク表示
  - 登録済み: 「トライアル中の投稿上限（60通）に達しました。基本料金が発生し投稿は
    課金されます」（リンクは非表示）
- **表示可否のスイッチはCookie（`trial_post_limit_notice`、Max-Age 3日、`path=/`）で
  持つ**。バナー条件を満たした際にCookieが無ければその場でセットし表示、既にあれば
  そのまま表示。**Cookieが無ければ（自然に3日経過して失効した場合・ユーザーが手動で
  削除した場合のいずれも）その場でバナーは表示しない**という単純なCookie依存の設計で、
  サーバー側に「初回表示日時」のような状態は一切持たせていない（仕様として明示的に
  「クッキーが削除されている場合はメッセージは表示しなくていい」と指定されたことに
  対応。Cookieが自然失効した後に再度条件を満たせば、Cookieが無い状態から再度
  3日間のカウントが始まる、というのが実装上の帰結）
- **トライアル終了案内バー（`trial-bar`）は、投稿上限に達している間は登録済み/
  未登録どちらの文言も表示しない（2026-08-25変更）**。表示条件を
  `me.status === "trial" && me.trialDisplayEndsAt && !me.trialPostLimitReached`に
  変更し、両文言とも投稿上限到達バーと重複表示されないようにした（それまでは
  「お客様は現在トライアル期間です」（登録済み分岐）のみ非表示にしていたが、
  未登録分岐の「◯日でトライアル期間が終了します。お支払い情報を登録すると…」も
  同様に非表示にすべきという指摘を受けて拡張した）
- `requireUnderTrialPostLimit`ミドルウェアが返す403のエラーメッセージ自体（上記）は
  変更していない。こちらは即時投稿・ワンショット予約投稿の送信操作に対する同期的な
  インラインエラー（one-shot-post.html）用であり、支払い方法登録状況を都度Stripeへ
  問い合わせるコストを投稿APIの都度発生させたくないため。今回追加した3日間表示の
  お知らせバナーとは別の表示経路のまま
- 継続スケジュール（post_schedules）由来の投稿がブロックされた場合、cronがバックグラウンドで
  実行するためユーザー操作に対する同期レスポンスが存在せず、この403メッセージ表示の
  仕組みには乗らない。ダッシュボードのバナーが実質的に唯一の通知経路になる

## トライアル投稿上限80%到達時の即時メール（2026-08-25追加）

投稿上限（`TRIAL_POST_LIMIT`=60通）の**80%（`TRIAL_POST_LIMIT_WARNING_COUNT`=48通、
`Math.ceil(60*0.8)`）に達した瞬間**に、上限到達を待たず即時メール送信する。

- `customerStore.crossedTrialPostLimitWarning(customer, beforeCount, afterCount)`
  （純粋関数）: `status==="trial"`かつ`beforeCount < 48 <= afterCount`を満たす場合のみ
  `true`。**「今回の加算で初めて48通ラインを跨いだか」を判定するだけの単純な比較**で、
  専用の送信済みフラグをmicroCMSに永続化する必要が無い設計（`trialPostCount`は同一
  トライアル期間中は増加し続けるだけで減らないため、この比較だけで「1トライアル期間に
  一度だけ」が保証される。新しいトライアルが始まれば`trialPostCount`が0に戻り、
  次のトライアルでも正しく再度判定される）
- 呼び出し元は`bumpTrialPostCount`と対になる3箇所（即時投稿・ワンショット予約投稿の
  `posts.js`2箇所、継続スケジュール投稿の`scheduledPostExecutor.js`）。いずれも
  `bumpTrialPostCount`実行の直前に`getTrialPostCount(customer)`で加算前の値を控え、
  実行後の戻り値と合わせて`crossedTrialPostLimitWarning`に渡す
- `true`の場合のみ`src/lib/trialPostLimitWarningMailer.js`の
  `sendTrialPostLimitWarningIfNeeded({customer, logger})`を呼ぶ
- メールテンプレートは`emailTemplates.js`の`TRIAL_POST_LIMIT_WARNING_EMAIL`
  （新規追加）。件名「無料トライアルの投稿数が上限に近づいています」、本文に
  現在の投稿数・上限数を含む
- **支払い方法登録の有無に関わらず必ず送信する（2026-08-25仕様変更）**。当初は
  「支払い方法登録済みなら送信しない」設計だったが、60通到達時の挙動が
  「未登録なら投稿停止／登録済みなら自動課金」に分かれる仕様（下記「投稿上限到達時の
  自動アクティベート」参照）になったため、それぞれの顧客に応じた案内を出し分けて
  必ず送るよう変更した:
  - 未登録: 「上限の60通に達すると、それ以降の投稿ができなくなります。トライアル
    期間中も引き続き投稿をご利用いただくには、お支払い情報のご登録が必要です。」＋
    `payment.html`へのリンク
  - 登録済み: 「上限の60通に達すると、登録済みのお支払い方法（クレジットカード）へ
    自動的に基本料金のご請求が開始され、引き続き投稿をご利用いただけます。」（リンク
    無し）
  - リンク先は`upgrade.html`ではなく**`payment.html`**（2026-08-25変更）。トライアル
    中にカードだけ先に登録しておけば、実際に60通へ到達した瞬間
    `trialLimitAutoActivation.js`が自動でサブスクリプションを作成し即時課金するため、
    Checkoutを手動で完了させる`upgrade.html`を経由する必要が無くなったため
- 送信失敗（Stripe API障害・SMTP障害等）は例外を投げず`false`を返す設計（メール
  送信の成否が投稿処理自体の成否に影響しない、`scheduleResultMailer.js`と同じ方針）
- **エッジケース**: `bumpTrialPostCount`は同時実行時の排他制御を持たない
  （既存の既知の制約、コード内コメント参照）ため、48通ライン付近で複数の投稿が
  ほぼ同時に成功した場合、理論上は警告メールが複数回送信される可能性がある
  （招待メンバー数上限チェックのレース条件と同種の、実運用上は許容されている
  既知のリスク）

## 投稿上限（60通）到達時の自動アクティベート・即時課金（2026-08-25新規追加）

投稿上限（60通）そのものに達した瞬間、**支払い方法（Stripeカード）を既に登録済みの
トライアル顧客は、ユーザー操作を挟まずサーバー側で自動的に本稼働へ切り替わり、
即時に基本料金の請求が開始される**。未登録の顧客は従来通り投稿がブロックされたままで、
何も自動では起きない。

### 判定と呼び出し（80%警告メールと対称の構造）

- `customerStore.crossedTrialPostLimit(customer, beforeCount, afterCount)`（純粋関数）:
  `crossedTrialPostLimitWarning`と全く同じ考え方で、`status==="trial"`かつ
  `beforeCount < 60 <= afterCount`のときのみ`true`。「今回の加算で初めて60通ラインを
  跨いだか」だけを見る単純な比較で、専用の永続フラグは不要
- 呼び出し元は80%警告メールと同じ3箇所（`posts.js`の即時投稿・ワンショット予約投稿、
  `scheduledPostExecutor.js`の継続スケジュール投稿）。`bumpTrialPostCount`実行の
  前後の値を`crossedTrialPostLimit`に渡し、`true`の場合のみ
  `src/lib/trialLimitAutoActivation.js`の`activateAfterTrialLimitIfNeeded({customer,
  logger})`を呼ぶ

### trialLimitAutoActivation.js（新規ファイル）

`activateAfterTrialLimitIfNeeded`の処理内容:

1. `trialPostLimitWarningMailer.customerHasPaymentMethod(customer.stripeCustomerId)`
   でStripeへ実問い合わせ。**未登録なら`"no_payment_method"`を返して何もしない**
   （＝`requireUnderTrialPostLimit`等の既存ブロックがそのまま効き、投稿停止状態が
   継続する）
2. 登録済みの場合、`stripePricing.pricesForPlan(planKey(customer))`でプランの
   base/metered/meteredX Price IDを取得し、`ensureStripeCustomer`でStripe Customer IDを
   確保した上で`stripe.subscriptions.create({customer, items:[...]})`を呼ぶ。
   **`create-checkout-session`（billing.js、通常のアップグレード手続き）とは異なり、
   意図的に`trial_end`を指定しない**。これにより作成と同時に最初のinvoiceが
   生成・確定され、Stripe顧客の`invoice_settings.default_payment_method`
   （`billing.js`の`payment-methods/confirm`でprimaryカード登録時に自動設定される）
   へ即座に請求される
3. 作成したサブスクリプションの`status`が`"active"`であることを確認してから
   `customerStore.updateCustomer`で`stripeSubscriptionId`・`status:["active"]`・
   `trialLimitAutoActivatedAt`（ISO日時、後述のダッシュボード通知用）を書き込む。
   **`status`が`"active"`以外（`"incomplete"`等、作成直後の決済失敗）の場合は
   `customer`を一切更新しない**（誤って本稼働扱いにしないため。トライアル扱い・
   投稿ブロックのまま据え置かれる）
4. いずれの分岐でも例外を投げず、`"activated"`/`"no_payment_method"`/`"failed"`の
   いずれかを返す（呼び出し元の投稿処理自体の成否には影響させない、他の非致命的
   副作用と同じ方針）

呼び出し元（`posts.js`・`scheduledPostExecutor.js`）は、`"activated"`が返った場合、
同一バッチ/同一リクエスト内で保持しているin-memoryの`customer`オブジェクトの
`status`も`["active"]`に更新する（`scheduledPostExecutor.js`のみ。`customerCache`を
cron実行内で使い回すため、`trialPostCount`更新と同じ理由）。

### 救済経路: 既にブロックされた後にカード登録した場合の再開（重要・2026-08-25追加）

上記の`crossedTrialPostLimit`は「60通ラインを跨いだその瞬間」しか検知できない
（`bumpTrialPostCount`は投稿が**成功**した時にしか呼ばれず、既にブロックされている
顧客の投稿はそもそも実行されないため、跨いだ後は二度と発火しない）。そのため、
「60通到達時点では未登録だったが、その後`payment.html`でカードを登録した」という
極めて起こりやすいケースを、`crossedTrialPostLimit`だけではカバーできない。

これを拾うため、**投稿をブロックする直前の3箇所すべてに、ブロックする前に
一度`activateAfterTrialLimitIfNeeded`を試みる救済ロジックを追加した**:

1. `requireUnderTrialPostLimit`ミドルウェア（`src/middleware/requireAuth.js`）:
   `isTrialPostLimitReached(req.customer)`がtrueになった時点で即403を返していたのを、
   403を返す前に`activateAfterTrialLimitIfNeeded`を呼び、`"activated"`なら
   `req.customer.status = ["active"]`にした上で`next()`（＝投稿を通す）。それ以外
   （未登録・失敗）は従来通り403
2. `scheduledPostExecutor.js`の`attemptScheduledPost`内、`isTrialPostLimitReached`
   チェックで即`throw`していた箇所も同様に、throwする前に一度試みる
3. `scheduleMaterializer.js`の生成前チェック（`isCanceled(customer) ||
   isTrialPostLimitReached(customer) || requiresPaymentRegistration(customer)`と
   まとめて`continue`していた）も、`isTrialPostLimitReached`の場合だけ切り出して
   同様に救済を試みるよう変更（`isCanceled`・`requiresPaymentRegistration`は本機能と
   無関係のため従来通り即`continue`）

いずれも`activateAfterTrialLimitIfNeeded`自体が内部で全例外を捕捉し
`"failed"`を返す設計（上記参照）のため、追加のtry/catchは不要。支払い方法が
未登録の顧客が投稿を試みるたびに`customerHasPaymentMethod`（Stripeへの問い合わせ）
が毎回実行される点は許容している（頻度・実運用上のコストとして問題にならない
という判断。Stripe API呼び出しがボトルネックになる規模になれば、結果を
一定時間キャッシュする等の対応を検討する）。

### 救済経路の穴: リアクティブな4箇所だけでは足りないケース（2026-08-25発見・修正）

上記の救済経路（`requireUnderTrialPostLimit`・`scheduledPostExecutor.js`の事前
チェック・`scheduleMaterializer.js`の生成前チェック）は、`crossedTrialPostLimit`と
合わせても**すべて「何かが実際に動くタイミング」でしか発火しない**。継続スケジュール
投稿だけを使っている顧客が、以下のような状態に入ると、支払い方法を登録済みでも
何日もアクティベートされないまま放置される：

- `scheduleMaterializer.js`は`last_materialized_dt`が当日と一致するスケジュールを
  即`continue`でスキップする（冪等性のため、[scheduleMaterializer.js](../src/scripts/scheduleMaterializer.js)
  参照）。**このスキップは`isTrialPostLimitReached`のチェックより前**に行われるため、
  「その日の分は既に生成済み」の状態に入った時点で、その日はもう救済チャンスが無い
  （曜日限定のスケジュールなら、次の該当曜日まで）
- 生成済みの`scheduled_posts`が0件（または既に全件実行・失敗済み）であれば、
  `scheduledPostExecutor.js`側の救済チェックも呼ばれる機会が無い
- 顧客がダッシュボードを見るだけで即時投稿・ワンショット予約投稿を一切試みなければ、
  `requireUnderTrialPostLimit`も呼ばれない

**実機で発生した実例（shin.takase@icloud.com、2026-08-25）**: 上記「継続スケジュール
投稿がtrialPostCountに反映されない不具合」の修正・デプロイと、影響を受けた顧客の
`trialPostCount`の手動補正（34→実際の投稿実績に合わせて143。前述の「未対応（データ
修正）」注記の通りコードによる自動遡及補正ではない）が同日中に行われた結果、この
顧客は「トライアル中・投稿数143（60通超過）・支払い方法登録済み」という、本来即座に
アクティベートされるべき状態になった。しかし継続スケジュール（3件、毎日投稿）は
いずれもその日の分を既に生成済み（`last_materialized_dt`が当日と一致）で、かつ
生成済みの`scheduled_posts`は既に全件実行済み（0件保留）だったため、上記4箇所の
いずれも再チェックされる機会がなく、支払い方法登録済みにもかかわらず翌日の
`scheduleMaterializer.js`実行までアクティベートされない状態で放置された（ダッシュボードの
投稿予定・ご請求予測が共にゼロ、請求情報に「請求履歴はまだありません」と表示される
症状として顧客から報告）。

**修正**: 上記4箇所とは独立に、「トライアル中かつ投稿数60通以上」の全顧客を毎時
横断的にスキャンして`activateAfterTrialLimitIfNeeded`を試みる日次（実際は毎時）cronを
新設した。

- `customerStore.listCustomersOverTrialPostLimit()`（新規関数）: microCMSの
  `status[contains]trial[and]trialPostCount[greater_than]59`フィルタで対象顧客を
  取得する（`listCustomersForTrialReminder`と同じフィルタ構築パターン）
- `src/scripts/trialPostLimitAutoActivationSync.js`（新規ファイル）: 候補顧客ごとに
  `activateAfterTrialLimitIfNeeded`を呼び、`"activated"`なら
  `sendTrialPostLimitReachedEmailIfNeeded`で通知メールも送る（救済経路の3箇所と
  同じく`"no_payment_method"`では送らない。ブロックされ続けている顧客の一覧を
  毎回スキャンする都合上、送ってしまうと該当顧客に何度も同じメールが飛ぶため）
- cronの実行間隔は他の日次バッチ（トライアル終了リマインド・auto-pause-sync等）より
  高頻度な**毎時**（`/etc/cron.d/edgeailab-net-trial-post-limit-auto-activation-sync`）。
  60通到達後は投稿がブロックされ続ける＝顧客体験に即座に影響するため、日次では
  取りこぼしの放置期間が長すぎると判断した
- 既存の4箇所（`crossedTrialPostLimit`発火時の3箇所＋リアクティブな救済経路3箇所）は
  そのまま残す。この新しいcronは「他のどの経路にも引っかからなかった場合の最終防衛線」
  という位置づけで、通常はリアクティブな経路の方が先に（＝より短い遅延で）アクティベート
  する

### この機能が既存の「支払い方法登録」の意味を変える点（重要）

これまで（2026-08-25の本機能追加前）は、`payment.html`（`setup-intent`+`confirm`）で
カードを登録するだけでは`customer.status`は`"trial"`のまま変化せず、投稿ブロック解除も
課金開始も一切起こらなかった（実際に本契約へ進むには`upgrade.html`／
`change-plan.html`経由のCheckoutが別途必要だった）。

本機能導入により、**`payment.html`でカードを事前登録しておけば、実際に60通へ到達した
瞬間に自動でサブスクリプションが作成され課金が始まる**ため、初めて`payment.html`単独の
登録が実質的な意味を持つようになった。ダッシュボードの投稿上限到達バナー・80%警告
メールの文言（「お支払方法を登録されると投稿が再開され、基本料金が発生し投稿は
課金されます」）は、この機能があって初めて正しい説明になる（本機能実装前は、
バナーが実際には起きない挙動を約束してしまっていた）。

### ダッシュボードへの通知（trialLimitAutoActivated）

自動アクティベートされると`customer.status`が`"trial"`から`"active"`へ変わるため、
`isTrialPostLimitReached(customer)`（`status==="trial"`が前提）は即座に`false`へ戻る。
投稿上限到達バナーを表示し続けるための`GET /api/auth/me`の`trialPostLimitReached`
フラグも同時に`false`になってしまうため、**別のフラグ`trialLimitAutoActivated`を
`safeCustomer()`に追加**した（`src/routes/auth.js`）。

- `trialLimitAutoActivated`は`customer.trialLimitAutoActivatedAt`（自動アクティベート
  実行時刻、ISO文字列）が存在し、かつ`Date.now() - trialLimitAutoActivatedAt <
  TRIAL_LIMIT_AUTO_ACTIVATED_NOTICE_WINDOW_DAYS`（=3日、ダッシュボード側のCookie
  表示期間と同じ値）を満たす間だけ`true`
- **`trialLimitAutoActivatedAt`自体はDBに永続的に残るが、`trialLimitAutoActivated`の
  計算は毎回「3日以内か」を判定し直す。** これにより、ダッシュボード側のCookieが
  自然失効した後も何ヶ月も先にこのフラグが`true`のままバナーが再表示され続ける、
  という事態を防いでいる（Cookie側は「3日間表示する」という単純な仕組みしか持たない
  ため、バックエンド側でも同じ3日間という期限を設けることで、Cookieが切れた後は
  自然にバナー自体が出せなくなるよう二重に制限している）
- ダッシュボード（`dashboard.html`）は、`me.status === "trial"`だけでなく
  `me.trialLimitAutoActivated`も条件に加えて投稿上限到達バナーの表示可否を判定する
  よう変更した（外部仕様参照）

### 不具合: microCMSスキーマに`trialLimitAutoActivatedAt`未追加によるサブスクリプション二重作成（2026-08-25発見・修正）

上記`trialLimitAutoActivatedAt`フィールドを追加した際、**microCMSの`customers`
コンテンツタイプ側にこのフィールドをスキーマとして追加する作業が漏れていた**。
`activateAfterTrialLimitIfNeeded`は、Stripeでのサブスクリプション作成（＝実際の課金）に
成功した直後、`updateCustomer(customer.id, { stripeSubscriptionId, status: ["active"],
trialLimitAutoActivatedAt })`でmicroCMSへ書き戻すが、この呼び出しがmicroCMS側の
`400 'trialLimitAutoActivatedAt' is unexpected key`で失敗し、`stripeSubscriptionId`・
`status`の更新も道連れで失敗していた。

これにより顧客の`status`が`"trial"`のまま残るため、毎時cron
（`trialPostLimitAutoActivationSync.js`）が同じ顧客を「未対応の候補」と誤認し続け、
**実行のたびに新しいStripeサブスクリプションを作成＝重複課金**が発生する状態になっていた。

**実機で発生した実例（shin.takase@icloud.com、2026-08-25）**: cronが11:15・12:15の
2回実行され、いずれもサブスクリプション作成自体は成功（プライマリカードへの決済も
成功）したが、直後のmicroCMS書き戻しが失敗。結果、有効なサブスクリプションが2本
（`sub_1U89tE...`・`sub_1U8ApK...`）作成され、¥1,480が2回課金される事態になった。
後発の`sub_1U8ApK...`をStripe側でキャンセル、対応する請求¥1,480を返金し、
先発の`sub_1U89tE...`を正規のサブスクリプションとしてmicroCMS側に手動で反映して是正した。

**恒久対応**: `customerStore.js`の`updateCustomer`に、microCMSスキーマに存在しない
フィールドを含むPATCHが`400 '<フィールド名>' is unexpected key`で拒否された場合、
そのフィールドだけを除いて自動的に再試行するフォールバックを追加した。これにより、
今後同様のスキーマ追加漏れが発生しても、`status`・`stripeSubscriptionId`等の重要な
更新は成功する（＝サブスクリプション二重作成という金銭的実害は再発しない）。

**未対応（TODO・要手動作業）**: microCMSの`customers`コンテンツタイプに
`trialLimitAutoActivatedAt`フィールド（テキスト型）自体はまだ追加されていない。
このフィールドはコンテンツAPIキーからは追加できず、microCMS管理画面での手動作業が
必要。追加されるまでは、上記フォールバックにより常にこのフィールドが除外されるため、
「投稿上限到達バナー」の`trialLimitAutoActivated`フラグ（直前の項目参照）は
**全顧客について常にfalseのまま＝バナーが一切表示されない**状態が続く。

## 支払い登録が必要かどうかの判定（2026-08-22改名・拡張）

`requiresPaymentRegistration(customer)`（customerStore.js、cron・requireAuth.js両方から
参照される純粋関数。旧名`isTrialExpiredWithoutPayment`）:
```js
if (customer.stripeSubscriptionId) return false;
const status = ...;
if (status === "canceled") return false;
if (status !== "trial") return true;          // reactivateCustomer後のstatus:"active"はここで即true
if (!customer.trialEndsAt) return false;
return new Date(customer.trialEndsAt).getTime() < Date.now();
```

判定対象が2種類に拡張されている:
- **トライアル中（status:"trial"）**: 従来通りtrialEndsAt（内部値・33日基準）を経過するまでは
  猶予する
- **トライアル以外・未払い（reactivateCustomer後のstatus:"active"）**: 猶予期間を設けず、
  stripeSubscriptionId未登録なら常に`true`。正規のStripe決済完了時は必ず
  stripeSubscriptionIdと同時にstatus:"active"がセットされるため、実際に課金済みの顧客が
  誤ってブロックされることはない

**注意（2026-08-25、トライアル終了リマインドメール改修時に判明）**: この関数は
「アクセス制限が必要か」を判定するものであり、**「支払い方法（カード）を登録済みか」
とは別の概念**。`billing.js`の`POST /api/billing/payment-methods/confirm`（お支払い
方法画面からのカード登録）はサブスクリプションを作成せず`customer.status`を"trial"の
まま維持するため、トライアル中に早々にカードだけ登録した顧客は
`requiresPaymentRegistration(customer)`が引き続き`false`（トライアル中なので当然）
のままだが、`stripeSubscriptionId`も空のまま。「カード登録済みかどうか」を知りたい
処理（ダッシュボードの`trial-bar`・`trial-limit-bar`表示、トライアル関連メールの
送信要否判定）は、`customer.status`や`stripeSubscriptionId`を見るのではなく、
`GET /api/billing/payment-methods`（フロント）またはStripeの`paymentMethods.list`
（cron。`trialPostLimitWarningMailer.customerHasPaymentMethod`参照）で実際のカード
登録状況を都度確認する必要がある。

利用箇所:
- `blockExpiredTrial`ミドルウェア（requireAuth.js）: SNS連携開始（OAuth authorize系
  エンドポイント）・投稿系エンドポイント（`POST /api/posts`・`POST /api/posts/schedule`・
  `POST /api/schedules`・`PATCH /api/schedules/:id`等）の両方に組み込まれている。該当すると
  `status==="trial"`なら`/upgrade.html?reason=trial_expired`、それ以外（再登録後の
  未払い）なら`/upgrade.html?reason=payment_required`へリダイレクト（2026-08-22実機検証済み:
  解約→同一メール再登録後、メール認証済みの状態で`POST /api/schedules`・
  `GET /oauth/x/authorize`双方が`reason=payment_required`へ302リダイレクトされることを確認）
- `scheduleMaterializer.js`: 該当顧客のスケジュールは新規のscheduled_posts生成対象から除外
- `scheduleAutoPauseSync.js`（日次cron、稼働確認済み・`/etc/cron.d/edgeailab-net-schedule-auto-pause-sync`
  で毎日4時登録）: 該当顧客の全post_schedulesを`auto_paused: true`にし、未実行のpending
  scheduled_postsを取り消す。復帰時（支払い登録等でrequiresPaymentRegistrationがfalseに
  戻った場合）はauto_pausedをfalseに戻す（ユーザー自身によるis_pausedには一切触れない）

## トライアル終了リマインドメール（2026-08-25改修）

`src/scripts/trialReminderCheck.js`（単発実行スクリプト、`/etc/cron.d/
edgeailab-net-trial-reminder-check`で**毎日9:00**に実行。2026-08-25に5:00→9:00へ
変更）。

### 改修前の仕様（〜2026-08-24）と問題点

- `customerStore.listCustomersWithUpcomingTrialEnd(3)`で、`isVerified: true` かつ
  `trialReminderSent: false` かつ `trialEndsAt`（内部値・33日基準）が3日以内の顧客を
  抽出し、該当者に1回だけTRIAL_ENDING_EMAILを送信していた
- **クエリに`status`によるフィルタが一切無かった**。支払い方法を登録していても
  `trialReminderSent`が未送信のままなら送られ続ける可能性があった（後述の通り、
  トライアル中の支払い方法登録は`customer.status`を"trial"のまま変えないため、
  この欠落は実害があった）

### 現在の仕様（2026-08-25〜）

- **送信タイミングを2回に分割**: 表向きの残り日数（`trialDisplayEndsAt`基準）が
  **5日以下**になった時点で1回、**2日以下**になった時点でさらに1回、それぞれ独立して
  送信する（`REMINDER_WINDOWS`配列で管理。各ウィンドウごとに専用の送信済みフラグ
  `trialReminder5DaySent`／`trialReminder2DaySent`を持つ）
- **抽出クエリ刷新**: `customerStore.listCustomersForTrialReminder(displayDaysBeforeEnd,
  sentField)`。`isVerified[equals]true`・`status[contains]trial`（statusはmicroCMSの
  セレクトフィールドのため`[contains]`。**このstatusフィルタが今回新規追加**）・
  `{sentField}[equals]false`・`trialEndsAt[less_than]{now+(displayDaysBeforeEnd+3)日}`
  （3は`TRIAL_INTERNAL_BUFFER_DAYS`。表向きの残り日数ベースの閾値を、格納されている
  生の`trialEndsAt`に対するフィルタへ変換している）
- **支払い方法登録済みなら送らない（2026-08-25新規追加）**: 各候補ごとに
  `trialPostLimitWarningMailer.customerHasPaymentMethod(customer.stripeCustomerId)`
  （Stripeの`paymentMethods.list`を実際に問い合わせる）を確認し、登録済みならメール
  送信をスキップする。**`customer.status`や`stripeSubscriptionId`だけでは判定できない
  点が肝**: `billing.js`の`POST /api/billing/payment-methods/confirm`（カード登録の
  確定）はサブスクリプションを作成せず、`customer.status`を"trial"のまま維持する設計
  のため（詳細は「支払い登録が必要かどうかの判定」節）。改修前はこの確認自体が存在せず、
  トライアル中に早々にカードを登録した顧客にも「まもなくトライアルが終了します」
  メールが送られ続ける可能性があった
- 送信をスキップした場合（支払い方法登録済み）も、実際に送信できた場合も、いずれも
  該当ウィンドウの`sentField`を`true`にする（毎日Stripeへ再問い合わせしないため）。
  **メール送信自体が失敗した場合のみ**`sentField`は立てず、翌日以降のcronで再試行する
- `daysLeft`（メール本文の「残り◯日」）は、改修前のように`trialEndsAt`から都度
  再計算するのではなく、**どちらのウィンドウがマッチしたか（5または2）をそのまま
  渡す**方式に変更した（旧実装は内部バッファ込みの`trialEndsAt`から計算していたため、
  表向きの残り日数とズレた値が本文に表示されるリスクがあった）

**要対応（未実施）**: microCMS `customers`スキーマへの`trialReminder5DaySent`・
`trialReminder2DaySent`フィールド（いずれも真偽値、デフォルトfalse）の手動追加が
必要（管理画面での追加を忘れると、notify_email等と同様に書き込みが黙って無視され、
毎日重複送信され続ける形で症状が出る）。旧`trialReminderSent`フィールドは廃止せず
残しているが、このcronスクリプトからはもう読み書きしない（過去の送信履歴として
残るのみ。`reactivateCustomer`が新規トライアル相当の顧客を作る際のリセット対象には
新フィールドとあわせて含めている）。

### cron登録の経緯（2026-08-22時点の記録）

仕様書作成時のレビューで、`docker-compose.yml`にサービス定義自体が存在せず、
`/etc/cron.d/`・root個人crontabのいずれにも対応するcron登録が無いことが判明した
（他の同種スクリプトは`profiles: manual`サービス定義＋CLAUDE.mdへのcrontab登録例が
あったのに対し、trialReminderCheck.jsだけが定義漏れだった）。おそらく本番で一度も
実行されていなかった。`docker-compose.yml`に`sns-poster-trial-reminder-check`
サービスを追加し登録した（`sns-poster-approval-expiry-check`と同一構成。
customerMailer経由の送信のため`network_mode: host`は不要）。

## 外部SaaS連携

- Stripe: trial_end設定はサインアップ時ではなく、実際のCheckout Session作成時
  （billing.js、外部仕様_アップグレード.md側）に行われる。トライアル終了リマインド
  メール・投稿上限80%到達メールは、送信要否判定のため`stripe.paymentMethods.list`
  を呼ぶ（2026-08-25追加。`trialPostLimitWarningMailer.customerHasPaymentMethod`）。
  投稿上限（60通）到達時の自動アクティベート（2026-08-25追加）は、
  `stripe.subscriptions.create`を`trial_end`無しで呼び、即時課金を発生させる
  （`trialLimitAutoActivation.js`。`create-checkout-session`とは別の、ユーザー操作を
  介さないサブスクリプション作成経路）
- メール送信: `customerMailer.js`経由（SMTP、`mail.edgeailab.net`宛の認証付き中継。
  障害通知専用の`mailer.js`＝ホストのpostfix 127.0.0.1:25宛とは別経路のため混同注意）
