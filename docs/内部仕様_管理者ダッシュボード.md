## 認証

アプリ側にログイン機能は無い。`edgeailab.net`のnginx（`edgeailab-net-static`
コンテナ、`proxy/edgeailab.net.conf`）で`location /admin/`・`location /api/admin/`
の両方にBasic認証（`auth_basic_user_file /etc/nginx/htpasswd-admin`）をかけている。
htpasswdファイルの実体は`deploy/xserver-vps/proxy/htpasswd/edgeailab.net-admin`
（`$apr1$`ハッシュ、`openssl passwd -apr1`で生成）。**`deploy/xserver-vps/`配下は
このリポジトリ・sns-posterリポジトリいずれの管理対象でもない**（gitリポジトリでは
ない、サーバー上の生設定ファイル）ため、htpasswdファイル自体はどこにもコミット
されていない。

`GET /api/admin/stats`（`src/routes/adminStats.js`）はアプリ層では`requireAuth`等の
ミドルウェアを一切挟んでいない。保護は完全にnginx側のBasic認証に依存する設計
（このエンドポイントを他の経路・別ドメインから直接叩けるようにしないこと）。

## src/lib/adminStats.js（`getAdminStats(stripe)`）

**集計は暦月（Asia/Tokyo）基準**。`monthRange(now, offset)`が
`[その月の1日0時, 翌月1日0時)`を返す。`billingCycle.js`の顧客ごとのStripe請求
サイクル基準とは意図的に別物（全顧客横断の集計を単純にするため）。

### 利用者数

- 現在の利用者数 = `customers.status !== "canceled"`の件数。**2026-09-05以降、
  日次バッチのキャッシュ値**（後述の「今月」スナップショットに同梱。リアルタイム
  表示は不要という前提のため、最大1日遅れになる）
- 前月キャンセル数 = `customer.canceledAt`が前月レンジ内の件数
  （`countCanceledInMonth`。月次バッチのキャッシュ値）
- 前月の利用者数 = 現在の利用者数（今月スナップショットの`current`）− 前月
  キャンセル数（前月スナップショットの`canceledLastMonth`）。要件どおりの単純差分で、
  新規契約による増加は考慮しない近似値（ユーザーへの回答時に明記済み）。両方とも
  キャッシュ値同士の引き算であり、`getAdminStats`自体はこの式の計算以外
  何もリクエスト時に行わない

`customers.canceledAt`は2026-09-02時点でCLAUDE.mdに「microCMSスキーマ未対応」と
記載されていたが、2026-09-05に確認したところ実データが入っており解消済み
（本機能の実装前に確認し、CLAUDE.mdの記載を更新すべき事項として把握）。

### 投稿数・売上高（`computePeriodStats`）

1回の顧客走査で投稿数集計と売上高集計を両方行う（`postingLogStore.
getActualPostCounts`の呼び出しを両者で共有し、二重フェッチを避けている）。

- 投稿数: 全顧客の`getActualPostCounts(customerId, start, end)`を合算（SNS毎・合計）
- 売上高: **`status === "active"`（本稼働中）の顧客のみ**対象（トライアル中は
  まだ課金されておらず、解約済みはサブスクリプション自体が無いため）。顧客ごとに
  `stripePricing.pricesForPlan(plan)`で従量料金Price ID・XサーチャージPrice IDを
  解決し、`stripeTierPricing.computePriceAmount`で金額化する。**Price取得は
  プランごと（basic/standard/advanced、最大3種）にキャッシュ**し、顧客ごとに
  都度`stripe.prices.retrieve`しない

**SNS毎の売上高按分について（重要）**: Stripeの従量料金は顧客ごとの「全SNS合計
投稿数」に対する階層価格（例: 150件まで¥30/件、以降¥20/件）で決まり、SNS単体の
金額という概念がそもそも存在しない。そのため`revenueCounts[platform]`は、顧客ごとに
計算した従量料金合計を、その顧客のプラットフォーム別投稿数の比率で按分した
**近似値**（`meteredRevenue * (platformCount / totalCount)`）であり、実際の請求
明細の内訳ではない。Xサーチャージ（`xSurcharge`）は実際のX URL付き投稿数から
個別に計算するため、近似ではなく正確な金額になる（2026-09-05、ユーザーへの
確認事項として明示済み）。

### 基本料金の追加・Xサーチャージの統合（2026-09-05再改修）

当初は「売上高には基本料金を含まない（従量料金・Xサーチャージのみ）」としていたが、
ユーザーからの追加要望で**基本料金も表示に含める**よう変更した。`computePeriodStats`
は本稼働中の顧客について、従量料金・Xサーチャージの計算と同じループ内で
`prices.base`（`pricesForPlanCached`が返す3点セットにbaseを追加）の
`unit_amount`を単純合計する（投稿数に依存しない固定額のため按分は不要）。

`getAdminStats`のレスポンス形は、キャッシュ内部の生データ（`total`＝従量料金合計、
`xSurcharge`、`baseFee`）を`buildRevenueView()`で表示用に整形する:
```js
{
  counts,          // SNS毎の従量料金按分値（Xサーチャージは含まない）
  meteredTotal,    // 従量料金の合計（= revenue.total、Xサーチャージ抜き）
  xSurcharge,
  usageTotal,      // meteredTotal + xSurcharge（画面の「従量料金合計」行に対応）
  baseFee,
  grandTotal,      // usageTotal + baseFee（画面の「合計」行に対応）
}
```
画面側（`admin/index.html`の`renderRevenueTable`）は、Xの行の直下に
「Xサーチャージ」をインデント付きのサブ行として描画し（**Xサーチャージは
独立したセクションではなくXの従量料金の内訳として表示**、旧4段目のXサーチャージ
専用カードは削除）、その後に従量料金合計・基本料金・合計を続けて表示する。

キャッシュファイル（`admin_stats_last_month.json`・`admin_stats_this_month.json`）
のスキーマも`revenue.baseFee`が追加されたため、**この変更をデプロイしたら両バッチを
手動で1回再実行してキャッシュを更新すること**（再実行しないと、次回バッチが自動実行
されるまで`baseFee`が欠けた古いキャッシュのままになる。フィールド欠落時は
`buildRevenueView`が`undefined`を返しNaN表示になる点に注意）。

## バッチキャッシュ化（2026-09-05、2段階で導入）

最初は前月分のみキャッシュ化し、今月分（今日まで）は毎リクエスト都度計算していた。
その後「今月分もリアルタイム表示は不要」というユーザー要望を受け、**今月分も
日次バッチでキャッシュ化し、`getAdminStats`のリクエスト処理からは全顧客横断の
計算（Stripe API呼び出し含む）を完全に排除した**（通常運用時は2つのJSONファイルを
読んでマージするだけ）。

### 前月分: `src/scripts/adminStatsMonthlyBatch.js`（月初1回）

前月分（利用者数のキャンセル数・投稿数・売上高）は、月が変わった後は絶対に値が
変わらない確定データなので、月1回の計算で十分。`computeAndCacheLastMonthStats`が
`json/admin_stats_last_month.json`へ書き込む。

```json
{
  "month": "2026-08",
  "generatedAt": "2026-09-01T00:10:00.000Z",
  "canceledLastMonth": 0,
  "posts": { "counts": {...}, "total": 4 },
  "revenue": { "counts": {...}, "total": 120, "xSurcharge": 0 }
}
```

cronは`sns-poster-admin-stats-monthly-batch`（`profiles: manual`）、
`/etc/cron.d/edgeailab-net-admin-stats-monthly-batch`に毎月1日0時10分で登録済み。

### 今月分・現在の利用者数: `src/scripts/adminStatsDailyBatch.js`（毎日4時）

今月分（今日までの投稿数・売上高）と現在の利用者数は生きた値だが、ダッシュボード
表示にリアルタイム性は不要という前提のため、トラフィックの少ない時間帯（毎日4時）に
1日1回計算すれば足りる。`computeAndCacheThisMonthStats`が
`json/admin_stats_this_month.json`へ書き込む（`current`＝現在の利用者数もここに
同梱。「生きた値だが日次更新で足りる」という同じ性質のため）。

```json
{
  "month": "2026-09",
  "generatedAt": "2026-09-05T19:00:00.000Z",
  "current": 4,
  "posts": { "counts": {...}, "total": 114 },
  "revenue": { "counts": {...}, "total": 3420, "xSurcharge": 736 }
}
```

cronは`sns-poster-admin-stats-daily-batch`（`profiles: manual`）、
`/etc/cron.d/edgeailab-net-admin-stats-daily-batch`に毎日4時0分で登録済み。

### getAdminStats: 通常時は2つのJSONを読むだけ

`GET /api/admin/stats`は、通常運用時は`admin_stats_last_month.json`と
`admin_stats_this_month.json`を読み込み、フィールドをマージして返すだけで、
`listAllCustomers`・`getActualPostCounts`・`stripe.prices.retrieve`のいずれも
呼ばない。レスポンスには`generatedAt.lastMonth`/`generatedAt.thisMonth`（各
キャッシュの生成時刻）を含め、管理画面側で「最終更新: …」として表示する
（表示データがリアルタイムでないことを利用者に明示するため）。

**安全側フォールバック**: 各キャッシュの`month`が「今から見た対象月」
（前月キャッシュは`monthRange(now, -1)`、今月キャッシュは`monthRange(now, 0)`）と
一致するかを毎回照合する。キャッシュが存在しない、または月がズレている
（バッチが未実行・失敗、cron未登録等）場合のみ、`console.warn`でログを残した上で
その場で`buildLastMonthSnapshot`／`buildThisMonthSnapshot`を呼びライブ計算に
フォールバックする（表示は壊れないが、本来避けたい重い処理が発生するため、
警告ログを運用監視の目印にする。通常運用では発生しない想定）。

## エッジケース・注意点

- `stripe.prices.retrieve`が失敗する（Price未設定等）プランの顧客は、売上高計算から
  黙って除外される（投稿数の集計には影響しない）
- 今月分は月末を待たず「バッチ実行時点（毎日4時）まで」を対象にする
  （`thisMonth.start`〜バッチ実行時の`now`）。月の最初の数日はサンプル数が少なく
  変動が大きい点に注意
- 今月分は最大約1日遅れ（前日4時時点のスナップショット）。当日分の投稿・解約は
  翌日4時のバッチまで反映されない

## 利用者一覧: src/routes/adminCustomers.js

`GET /api/admin/customers`（`email`・`status`・`page`クエリ）は
`customerStore.listCustomersFiltered`（新規追加）を使い、microCMS側で
`orders=-createdAt`・`filters`（`email[contains]`・`status[contains]`）・
`limit`/`offset`を指定してサーバー側フィルタ・ページングする（`listAllCustomers`の
ような全件取得はしない。顧客数が増えても軽い）。`status`はセレクト項目のため
既存の慣習どおり`[contains]`を使う（`[equals]`は空配列に落ちて常にヒットしない
バグの原因になる。CLAUDE.md・過去のscheduled_posts事故参照）。

`GET /api/admin/customers/:id`は`getCustomerById`をそのまま使い、
Stripe ID・パスワードハッシュ・各種トークン・sessionVersion等を含まない
プロジェクションだけを返す（要件の「システムの制御に係るような細かい情報は
不要」に対応）。

利用開始日は`customers`スキーマの独自フィールドではなく、microCMSが自動付与する
`createdAt`をそのまま使う（customerStore.jsに`signedUpAt`のような専用フィールドは
存在しないため）。

## 投稿一覧: src/routes/adminPosts.js

`posting_logs`（成功のみ記録）と`announcementStore.listAllOfType("post_failure")`
（お知らせ機能が最終失敗のみ記録。src/lib/postFailureAnnouncer.js参照）を1本の
タイムラインにマージして表示する。posting_logsは投稿失敗を一切記録しないため、
失敗の実データはお知らせストアが唯一の情報源であり、**2026-09-05（お知らせ機能
導入日）より前の失敗は表示できない**。

このため、`announcementStore.createAnnouncement`とその呼び出し元
`postFailureAnnouncer.announcePostFailure`に`platform`・`createdBy`を構造化
フィールドとして追加した（従来はtitle/bodyの文字列にのみ含まれ、プログラムから
再利用できなかった）。既存の呼び出し元（`posts.js`・`scheduledPostRetryRunner.js`）
も対応するフィールドを渡すよう更新済み。

`listAllPostingLogsAcrossCustomers`（`postingLogStore.js`新規追加）は
`customer_code`フィルタ無しで全件を`orders=-posted_at`でページング取得する。
成功・失敗の両リストを全件メモリ上に読み込んでマージ・ソートしてから
50件ずつスライスする方式（`adminStats.js`導入前のライブ計算と同じ設計判断）。
投稿数が増えると重くなる点はadminStats.jsのバッチキャッシュ化と同様の将来課題
（まずはシンプルな実装を優先し、必要になったらキャッシュ化を検討する）。

管理者のメールアドレスは、`customer_code`＋`created_by`（userId）のペアを
`listAllCustomers`で構築したマップから解決する（announcementStore側の
`createdBy`も同じuserIdの意味で統一している）。

## パスワード初期化: src/routes/adminPasswordReset.js

`customerStore.adminSetPassword(email, passwordHash)`（新規追加）は、
`findCustomerAndUserByEmail`でユーザーを特定し、`resetPassword`（トークン検証済み
パスワード再設定）と同じ書き込みパターン（`passwordHash`更新＋`sessionVersion`
インクリメントで既存セッションを無効化）を、トークン無しで直接行う。

`src/lib/passwordGenerator.js`（新規）は誤読しやすい文字（`0/O`・`1/l/I`等）を
除いた文字集合から`crypto.randomInt`で12文字を生成する。既存コードベースには
人間可読なパスワード生成ユーティリティが無かったため新設した（既存の
`crypto.randomBytes`系はすべてトークン用の16進/base64url文字列で、パスワードとして
人が入力するには不向き）。

生成したパスワードは`ADMIN_PASSWORD_RESET_EMAIL`（`emailTemplates.js`新規追加）で
本人にメール送信するのみで、管理者のレスポンスには含めない（画面上に新パスワードを
表示しない）。メール送信失敗時（`sendCustomerMail`が`{ok:false}`を返す）は、
パスワード自体は既に変更済みである旨を含む502エラーを返す（変更がロールバック
されるわけではない点に注意）。

## Xサーチャージ: src/lib/xSurchargeStore.js, src/routes/adminXSurcharge.js, src/scripts/xSurchargeScheduleApply.js

### なぜconfig/surcharge.jsonをそのまま使わなかったか

`config/`はDockerfileで`COPY config ./config`されるため、実行時に書き換えても
**次回のコンテナ再作成・イメージ再ビルドで消える**（`json/`と違いbind mountされて
いない）。予約適用バッチが実行時に金額・Price IDを更新する必要があるため、
新規に`json/x_surcharge_current.json`（bind mount済みの`json/`配下、
`xSurchargeStore.js`が読み書き）を導入し、こちらを実行時の唯一の情報源とした。
未設定の間（バッチが一度も走っていない導入直後）は、従来どおり
`config/surcharge.json`・`STRIPE_PRICE_*_METERED_X`環境変数にフォールバックする
（`getCurrentAmountJpy`・`stripePricing.pricesForPlan`参照）。

### stripePricing.pricesForPlan(plan)の変更

`meteredX`のPrice IDだけ、`xSurchargeStore.getCurrentPriceId(plan)`（実行時
オーバーライド）が存在すればそちらを優先し、無ければ従来どおり環境変数を返す。
`base`・`metered`（Xサーチャージ以外の従量料金）は今回のスコープ外のため変更していない。
この関数は`billing.js`（チェックアウトセッション作成）・`adminStats.js`・
`addXSurchargePriceItems.js`等、既存の全呼び出し元から間接的に新価格を拾えるように
なる（呼び出し元の変更は不要）。

### xSurchargeScheduleApply.js（予約適用バッチ、cron）

`addXSurchargePriceItems.js`と同じ安全策として、デフォルトはdry-run
（`--apply`を付けて初めて実際に変更する）。cronの`docker compose run`コマンドには
`--apply`を付けて登録済み（`/etc/cron.d/edgeailab-net-x-surcharge-schedule-apply`、
毎日4時20分）。

適用手順（`--apply`時）:
1. プラン（basic/standard/advanced）ごとに現在のmeteredX Priceを取得し、
   その`product`に対して新しい`unit_amount`のPriceを新規作成する（Stripe Priceは
   immutableなため、金額変更＝新規Price作成＋差し替えでしか実現できない）。
   1つでも作成に失敗したら、他のプランも含め一切の変更を行わず中断する
   （部分適用を避けるため、顧客のサブスクリプションには一切触れる前に中断する）
2. `stripeSubscriptionId`を持つ解約済みでない全顧客について、対象プランの
   現在のmeteredX Priceが付いている`subscriptionItem`を新Priceに差し替える
   （`proration_behavior: "none"`＝日割り課金しない。差し替え以降の投稿分から
   新料金が適用される）。顧客ごとの失敗は他顧客の処理を止めず、最後に集計する
3. `xSurchargeStore.setCurrent`で新しい金額・Price IDを保存する。以降
   `pricesForPlan`がこちらを返すようになり、**新規契約者にも新料金が自動的に
   適用される**
4. 予約を削除する（`clearReservation`）

顧客ごとの差し替えに1件でも失敗した場合、`notifyFailure`（社内運用向け障害通知）
で運営者にアラートする（財務に関わる操作のため、部分失敗を静かに終わらせない）。
Price作成自体が失敗した場合も別途アラートする。

**実機確認（2026-09-05、dry-runのみ）**: 本番のStripeデータに対してdry-runを実行し、
本稼働中の3顧客それぞれで正しいsubscriptionItemが特定できることを確認済み
（トライアル中・解約済みの顧客は正しく対象外になることも確認済み）。`--apply`での
実際の適用（Price作成・サブスクリプション差し替え）は本番データに対して未実施
（財務影響があるため、実際の予約が入って初めて実行される）。

### referenceUsd（Xサイト参照値）を自動取得にしなかった理由

`https://developer.x.com/`配下の複数ページへWebFetchを試みたが、いずれも
HTTP 402 Payment Requiredが返り、自動アクセスができないことを実機確認した
（2026-09-05）。安定した取得手段が無いため、管理者が手入力し
`xSurchargeStore.setXReferenceUsd`で保存する方式にした。

### ドル円レート

`https://open.er-api.com/v6/latest/USD`（無料・APIキー不要、`exchangerate-api.com`
提供）から取得する。`GET /api/admin/x-surcharge`のリクエストごとに都度取得する
（キャッシュしない。1日1回程度しか更新されないAPIだが呼び出し自体は軽量なため）。
取得失敗時はその項目のみnullを返し、他の情報（現在額・参照値等）は表示できる
ようにする。

## サーバーのリソース状況: src/routes/adminServerResources.js

コンテナはホストとカーネル・cgroupを共有しており、`os.cpus()`（CPU数・型番）・
`os.loadavg()`・`os.totalmem()`/`os.freemem()`・`df -k /`（overlay filesystem、
実体はホストの`/dev/vda1`）のいずれもホストの実値と一致することを実機で確認済み
（2026-09-05、`docker exec`でコンテナ内外の値を比較）。ホスト側に別途常駐
スクリプトを用意する必要はなく、コンテナ内から直接読める。外部API呼び出しが無く
軽量なため、`adminStats.js`とは異なりバッチキャッシュ化はせず、リクエストのたびに
その場で計算する（画面にも「更新」ボタンがあり、都度最新値を取得する設計）。
