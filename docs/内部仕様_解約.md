## APIエンドポイント

| メソッド | パス | 認証 | 概要 |
|---|---|---|---|
| POST | /api/account/cancel | requireAuth（管理者ロール限定） | アカウント解約 |

## 権限チェック

```js
if (currentUserRole(req.user) !== "管理者") return 403;
```
team.jsのメンバー招待と同じ方針で、アカウント全体（サブスクリプション・全メンバーの
SNS連携）に影響する操作のため管理者のみに限定している。

## 処理フロー（順序が重要）

1. 管理者ロール確認（上記）
2. Stripeサブスクリプションのキャンセル
   - `customer.stripeSubscriptionId`があれば`stripe.subscriptions.cancel(...)`を呼ぶ
   - Stripe側が失敗（APIエラー、またはSTRIPE_SECRET_KEY未設定）しても、解約フロー全体は
     止めない（顧客からは解約済みに見えるべき、というコード内コメントの方針）。
     失敗時は運用者宛に`notifyFailure`メールを送り、`customers.status`の更新自体は続行する
     （Stripe側の手動解約が別途必要になる旨をメール本文に明記）
   - **請求タイミングに関する注意（2026-09-02修正）**: Stripe公式ドキュメント
     （`DELETE /v1/subscriptions/:id`）によれば`invoice_now`のデフォルトは**`false`**
     であり、2026-08-22時点でこのドキュメントに書かれていた「デフォルトがtrue」という
     記述は誤りだった（実際に検証しないままFAQ整備時のレビューで確定事実として
     書かれてしまっていた）。このためオプション無しで呼んでいた間は、解約時点までの
     未確定分（従量料金・Xサーチャージ等のStripe Billing Meter使用量）を含めた最終請求書が
     一切発行されず、当該期間の従量課金がそのまま切り捨てられていた
     （2026-09-02、shin.takase@icloud.comの実解約でStripe Billing Meterに99件の
     `post_created`イベントが未請求のまま残っていたことを実データで確認）。
     `stripe.subscriptions.cancel(subscriptionId, { invoice_now: true, prorate: false })`
     に修正し、解約と同時に未確定の従量分を最終請求書として即時発行するようにした。
     `prorate: false`は基本料金（固定費）側の日割り調整をしないため（基本料金は月初一括
     請求済みで日割り返金の対象外という既存の請求方針に合わせる）。
3. **カード情報の削除（2026-08-22実装）**: `customer.stripeCustomerId`があれば、
   `stripe.paymentMethods.list({customer: stripeCustomerId, type: "card"})`で
   登録済みカードを全件取得し、1件ずつ`stripe.paymentMethods.detach(pm.id)`を実行する。
   サブスクリプションキャンセルと同様、失敗しても解約フロー全体は止めず
   `notifyFailure`メールで運用者に通知する（Stripe未設定時はログ出力のみ）。
   **それまでは検討漏れで未実装であり、解約後もStripe顧客にカードが残り続けていた**
   （FAQ「解約した場合は自動的にカード情報は削除されます」の実装レビューで発覚）
4. 連携中の全SNSプラットフォーム（facebook/instagram/threads/x）のトークンを
   `tokenStore.deletePlatformTokensBySlug`で削除
5. **`deleteAllScheduledPostsForCustomer(customerId)`**（2026-08-22実装。
   2026-09-02に全件削除へ拡張）:
   `scheduledPostStore.listAllScheduledPostsForCustomer(customerId)`で該当顧客の
   scheduled_posts**全件**（スケジュール投稿由来・ワンショット予約由来の両方、
   status不問）を取得し、1件ずつ`deleteScheduledPost`で削除する（microCMSへの
   並行書き込みが429で弾かれるため、1件ずつ順番に処理する既存パターンに合わせている）。
   **2026-09-02までは`listPendingByCustomer`でstatus=pending分のみ削除し、
   done/failed（投稿一覧・請求内訳計算用の実績履歴）は残す設計だった**が、「解約＝
   顧客データの物理削除」という方針への変更に伴い全件削除に拡張した（post-list.html・
   billing-history.htmlはいずれも解約後customersレコードごと消えてログインできなく
   なるため、履歴を残す実利がないと判断）。戻り値の削除件数をログに記録する。
6. **`deletePostingLogsForCustomer(customerId)`**（2026-09-02実装）:
   `postingLogStore.listAllPostingLogsForCustomer(customerId)`で該当顧客の
   posting_logs（投稿済みログ）全件を取得し、1件ずつ`deletePostingLog`で削除する
   （5.と同じ理由・同じ429対策）。
7. **`deleteSchedulesForCustomer(customerId)`**（2026-09-02実装）:
   `scheduleStore.listSchedulesForCustomer(customerId)`で該当顧客の全post_schedules
   （継続投稿の定義）を取得し、各スケジュールについてまず`scheduleTextStore.
   listScheduleTexts(schedule.id)`で紐づくschedule_texts（投稿文章。schedule_id経由
   でのみ辿れるためpost_schedules起点で列挙）を全件`deleteScheduleText`で削除してから、
   `scheduleStore.deleteSchedule`でスケジュール自体を削除する（5.と同じ理由で
   1件ずつ順番に処理）。**それまではpost_schedules・schedule_texts自体を
   削除・一時停止しておらず**、「`scheduleMaterializer.js`が`customers.status=
   "canceled"`の顧客を生成対象から除外するため解約後に新規のscheduled_postsが
   生成されることはない」という想定に頼っていたが、これは**同一customerIdでの
   再サインアップ（`customerStore.reactivateCustomer`）を考慮していなかった**。
   再登録して本契約（Stripe Checkout完了）が済むと`isCanceled`・
   `requiresPaymentRegistration`の両ガードが即座に外れるため、解約前の古い
   post_schedulesがそのまま生成・投稿を再開してしまう実害のある不具合になっていた
   （2026-09-02、`biza3cp70`の実機再現で確認。解約前に設定していたスケジュールが
   再登録・本契約完了の直後にscheduled_postsを生成し、実際に投稿まで完了していた）。
8. アカウント本人・招待メンバー全員の`users[].sessionVersion`をインクリメントし、
   発行済みの全セッション（本人・全メンバー、他デバイス・他ブラウザ含む）をサーバー側で
   無効化する。`clearSessionCookie`はブラウザにCookie削除を指示するだけでJWT自体は
   失効させないため、この処理が無いと解約後も既存セッショントークンで認証済みAPIを
   叩き続けられてしまう（コード内コメントで明記）
9. `customerStore.updateCustomer`で`status: ["canceled"]`と更新済みusers配列を書き込み
10. `clearSessionCookie`でCookie削除、`{ok: true}`を返す

## 設計上の二重防御

`requireAuth.js`の`blockCanceledCustomer`ミドルウェア（`isCanceled`判定）が、解約済み
顧客による書き込み操作を別途ブロックする。これは上記4.のSNS連携解除の実装漏れに対する
保険であり、両方が働いても問題ない設計（コードコメントに明記）。

`scheduledPostExecutor.js`も実行直前に`isCanceled(customer)`をチェックし、該当すれば
`account_canceled`エラーを投げて投稿を実行しない（4.に実装漏れがあった場合の三重目の防御）。

## customersレコードは削除しない

`status`を`"canceled"`に変更するのみで、レコード自体は削除しない。理由: 同一emailでの
再サインアップ時に`customerStore.reactivateCustomer`で既存レコードを再利用するため
（コードコメントに明記）。**2026-08-22修正**: `reactivateCustomer`はトライアルを
付与しない（`status`を"trial"にせず"active"に、`trialEndsAt`は空にする）よう
修正済み。詳細は内部仕様_無料で始める（トライアル）.mdの「トライアル開始」節を参照。

- customers: 読み取り `stripeSubscriptionId`, `users`／書き込み `status`,

- scheduled_posts: 読み取り `customer_code`／削除（DELETE。2026-09-02より全件対象。

- posting_logs: 読み取り `customer_code`／削除（DELETE。2026-09-02追加）
- post_schedules: 読み取り `customer_code`／削除（DELETE。2026-09-02追加）

## エッジケース・注意点

- Stripe解約が失敗しても`customers.status`は`canceled`に更新されるため、Stripe側と
  内部状態が一時的に不整合になりうる（運用者への通知メールで手動対応を促す設計）
- 解約は取り消し不可能な即時実行操作であり、確認ステップはモーダル1回のみ
  （パスワード再入力等の追加確認はない）
- カードdetachはサブスクリプションキャンセルの**後**に実行する。キャンセル時に
  Stripeが最終請求書の決済を試みる可能性があるため、先にカードを外すと正当な
  最終決済の妨げになりうるため（実装上の順序はこの意図を反映している）
- カードdetach失敗もサブスクリプションキャンセル失敗と同様、解約フロー自体は
  止めず`notifyFailure`メールのみで運用者に通知する（`customers.status`は
  `canceled`に更新される）ため、Stripe側にカードが残ったまま`canceled`になる
  ケースが理論上ありうる
- `invoice_now: true`による最終請求書の決済が失敗した場合（カード拒否等）も、
  既存のtry/catchでエラーを捕捉し`notifyFailure`メールのみで運用者に通知する設計
  （解約フロー自体は止めない）。Stripe管理画面での個別対応が必要になる
- post_schedules・schedule_texts・posting_logs・scheduled_posts（done/failed含む）の
  削除は解約時点で確定的に行われるため、後から「解約を取り消して元に戻す」手段は無い。
  誤って解約した場合、顧客は同一メールで再サインアップできるが（`reactivateCustomer`）、
  以前設定していた継続投稿のスケジュール・投稿実績履歴は復元されない
  （SNS連携・カード情報も同様に復元されない）
- posting_logs・scheduled_postsを解約時に全件削除するため、**Stripeの確定済み請求書
  （invoice）と突き合わせる社内側の実績記録が解約後は残らない**。Stripe側の請求書
  自体はStripeの仕様上API経由で削除できず（会計記録のため）残り続けるが、「何件・
  どのプラットフォームに投稿してその金額になったか」の内訳をmicroCMS側から
  事後的に検証する手段は解約と同時に失われる（2026-09-02の方針決定で許容）
