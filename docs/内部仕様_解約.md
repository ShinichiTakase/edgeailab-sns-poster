# 内部仕様: 解約

最終更新日: 2026-08-22（更新: カード自動削除の実装を反映）
コード参照: sns-poster/src/routes/account.js, sns-poster/src/lib/scheduledPostStore.js
（listPendingByCustomer）, sns-poster/src/lib/tokenStore.js, sns-poster/src/lib/customerStore.js

## APIエンドポイント

| メソッド | パス | 認証 | 概要 |
|---|---|---|---|
| POST | /api/account/cancel | requireAuth（管理者ロール限定） | アカウント解約 |

## 権限チェック

```js
if (currentUserRole(req.user) !== "管理者") return 403;
```
team.jsのメンバー招待と同じ方針で、アカウント全体（サブスクリプション・全メンバーの
SNS連携）に影響する操作のため管理者のみに限定している。

## 処理フロー（順序が重要）

1. 管理者ロール確認（上記）
2. Stripeサブスクリプションのキャンセル
   - `customer.stripeSubscriptionId`があれば`stripe.subscriptions.cancel(...)`を呼ぶ
   - Stripe側が失敗（APIエラー、またはSTRIPE_SECRET_KEY未設定）しても、解約フロー全体は
     止めない（顧客からは解約済みに見えるべき、というコード内コメントの方針）。
     失敗時は運用者宛に`notifyFailure`メールを送り、`customers.status`の更新自体は続行する
     （Stripe側の手動解約が別途必要になる旨をメール本文に明記）
   - **請求タイミングに関する注意**: `stripe.subscriptions.cancel(...)`はオプション
     無しで呼んでいるため、Stripeのデフォルト動作により、その時点までの未確定分
     （従量料金・Xサーチャージ等）を含めた**最終請求書がキャンセルと同時に即時発行
     される**（`invoice_now`のデフォルトが`true`）。「次回の請求にまとめて計上される」
     動作ではない点に注意（2026-08-22、FAQ整備時のレビューで明確化）
3. **カード情報の削除（2026-08-22実装）**: `customer.stripeCustomerId`があれば、
   `stripe.paymentMethods.list({customer: stripeCustomerId, type: "card"})`で
   登録済みカードを全件取得し、1件ずつ`stripe.paymentMethods.detach(pm.id)`を実行する。
   サブスクリプションキャンセルと同様、失敗しても解約フロー全体は止めず
   `notifyFailure`メールで運用者に通知する（Stripe未設定時はログ出力のみ）。
   **それまでは検討漏れで未実装であり、解約後もStripe顧客にカードが残り続けていた**
   （FAQ「解約した場合は自動的にカード情報は削除されます」の実装レビューで発覚）
4. 連携中の全SNSプラットフォーム（facebook/instagram/threads/x）のトークンを
   `tokenStore.deletePlatformTokensBySlug`で削除
5. **`cancelScheduledJobsForCustomer(customerId)`**（2026-08-22実装）:
   `scheduledPostStore.listPendingByCustomer(customerId)`で該当顧客の全pending予約投稿
   （スケジュール投稿由来・ワンショット予約由来の両方）を取得し、1件ずつ
   `deleteScheduledPost`で削除する（microCMSへの並行書き込みが429で弾かれるため、
   1件ずつ順番に処理する既存パターンに合わせている）。戻り値の削除件数をログに記録する。
   post_schedules定義自体は削除・一時停止しないが、`scheduleMaterializer.js`が
   `customers.status="canceled"`の顧客を生成対象から除外するため、解約後に新規の
   scheduled_postsが生成されることはない
6. アカウント本人・招待メンバー全員の`users[].sessionVersion`をインクリメントし、
   発行済みの全セッション（本人・全メンバー、他デバイス・他ブラウザ含む）をサーバー側で
   無効化する。`clearSessionCookie`はブラウザにCookie削除を指示するだけでJWT自体は
   失効させないため、この処理が無いと解約後も既存セッショントークンで認証済みAPIを
   叩き続けられてしまう（コード内コメントで明記）
7. `customerStore.updateCustomer`で`status: ["canceled"]`と更新済みusers配列を書き込み
8. `clearSessionCookie`でCookie削除、`{ok: true}`を返す

## 設計上の二重防御

`requireAuth.js`の`blockCanceledCustomer`ミドルウェア（`isCanceled`判定）が、解約済み
顧客による書き込み操作を別途ブロックする。これは上記4.のSNS連携解除の実装漏れに対する
保険であり、両方が働いても問題ない設計（コードコメントに明記）。

`scheduledPostExecutor.js`も実行直前に`isCanceled(customer)`をチェックし、該当すれば
`account_canceled`エラーを投げて投稿を実行しない（4.に実装漏れがあった場合の三重目の防御）。

## customersレコードは削除しない

`status`を`"canceled"`に変更するのみで、レコード自体は削除しない。理由: 同一emailでの
再サインアップ時に`customerStore.reactivateCustomer`で既存レコードを再利用するため
（コードコメントに明記）。**2026-08-22修正**: `reactivateCustomer`はトライアルを
付与しない（`status`を"trial"にせず"active"に、`trialEndsAt`は空にする）よう
修正済み。詳細は内部仕様_無料で始める（トライアル）.mdの「トライアル開始」節を参照。

## 外部SaaS連携

- Stripe: `stripe.subscriptions.cancel(stripeSubscriptionId)`（1回のみ。デフォルト
  動作により最終請求書を即時発行）
- Stripe: `stripe.paymentMethods.list({customer, type:"card"})` →
  `stripe.paymentMethods.detach(pm.id)`（登録カード数分。2026-08-22追加）

## microCMSスキーマへのI/O

- customers: 読み取り `stripeSubscriptionId`, `users`／書き込み `status`,
  `users[].sessionVersion`
- scheduled_posts: 読み取り `customer_code`, `status`／削除（DELETE）

## エッジケース・注意点

- Stripe解約が失敗しても`customers.status`は`canceled`に更新されるため、Stripe側と
  内部状態が一時的に不整合になりうる（運用者への通知メールで手動対応を促す設計）
- 解約は取り消し不可能な即時実行操作であり、確認ステップはモーダル1回のみ
  （パスワード再入力等の追加確認はない）
- カードdetachはサブスクリプションキャンセルの**後**に実行する。キャンセル時に
  Stripeが最終請求書の決済を試みる可能性があるため、先にカードを外すと正当な
  最終決済の妨げになりうるため（実装上の順序はこの意図を反映している）
- カードdetach失敗もサブスクリプションキャンセル失敗と同様、解約フロー自体は
  止めず`notifyFailure`メールのみで運用者に通知する（`customers.status`は
  `canceled`に更新される）ため、Stripe側にカードが残ったまま`canceled`になる
  ケースが理論上ありうる
