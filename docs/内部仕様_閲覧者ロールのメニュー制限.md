## 背景

メンバー招待機能（[内部仕様_メンバーを招待する.md](内部仕様_メンバーを招待する.md)）の
4ロール（管理者・承認者・編集者・閲覧者）のうち、「閲覧者」ロールについて
サイドバーメニュー項目ごとの使用可否を2026-08-27に明文化・実装した。

## メニュー項目ごとの使用可否（仕様）

| メニュー項目 | 使用可否 | 内容 |
|---|---|---|
| ダッシュボード | 使用可 | 制限なし |
| SNS連携 | 制限付き使用可 | 連携状況の表示のみ。連携・削除は使用不可 |
| スケジュール投稿 | 使用不可 | メニュー非表示＋ページ自体アクセス不可 |
| ワンショット投稿 | 使用不可 | メニュー非表示＋ページ自体アクセス不可 |
| 投稿一覧 | 使用可 | 制限なし |
| メンバーを招待する | 制限付き使用可 | 一覧の表示のみ。招待は使用不可 |
| 請求情報 | 使用可 | 制限なし |
| お支払い方法 | 制限付き使用可 | カード情報の表示のみ。追加／削除／プライマリ・バックアップ入替は使用不可 |
| FAQ | 使用可 | 制限なし |
| アップグレード | 使用不可 | メニュー非表示＋ページ自体アクセス不可 |
| ログアウト | 使用可 | 制限なし |
| プロフィール | 制限付き使用可 | 解約のみ使用不可（従来からの実装） |

## 実装方針（フロント＋サーバーの二重防御）

各制限は基本的に「フロント側でUIを隠す／リダイレクトする」＋「サーバー側APIでも
同じロールチェックを行う」の二重構成にしている。フロント側の制御はURLを直接
知っている場合や開発者ツールでのDOM改変では防げないため、フロント側の対応
だけをセキュリティ境界として扱わないこと。

### 「使用不可」項目（スケジュール投稿・ワンショット投稿・アップグレード）

- **サイドバー非表示**: `js/role-nav.js`の`insertRoleNavItems(role)`が、
  role === "閲覧者"のとき`.sidebar-nav`から`schedule-list.html`・
  `one-shot-post.html`へのリンク、`.sidebar-footer`から`change-plan.html`への
  リンクを削除する。
- **ページ直アクセス対策**: 同ファイルに新設した`redirectIfViewerForbidden(role)`を、
  schedule-list.html・schedule-form.html・schedule-detail.html・
  one-shot-post.html・change-plan.htmlの各`init()`内、`/api/auth/me`取得直後・
  他の初期化処理より前に呼ぶ。role === "閲覧者"なら`dashboard.html`へ
  `location.href`でリダイレクトしtrueを返す（呼び出し側は`if (...) return;`で
  以降の処理を止める）。change-plan.htmlは元々サイドバーが他画面と別実装
  （静的マークアップで`insertRoleNavItems`を呼んでいない）だったため、
  このページには`redirectIfViewerForbidden`呼び出しのみ追加し、
  `js/role-nav.js`の読み込み自体も新規に追加した。
- **サーバー側**:
  - `schedules.js`: `GET /api/schedules`・`GET /api/schedules/:id`・
    `GET /api/schedules/:id/texts`に`blockViewerRole`を追加（書き込み系の
    POST/PATCH/DELETEは既存で対応済み）。
  - `scheduleVideos.js`: `GET /api/schedules/:id/texts/videos/jobs/:jobId`に
    `blockViewerRole`を追加（他の3ルートは既存で対応済み）。
  - `billing.js`: `POST /api/billing/change-plan`に`blockViewerRole`を追加
    （このルートは元々ロール制限が一切無かった）。

### 「制限付き使用可」項目

#### SNS連携（onboarding.html・dashboard.htmlのSNSアイコン）

- フロント: `onboarding.html`の`renderRow()`が`isViewer`のとき「連携する」
  リンクの代わりに非活性表示（`.platform-connect.is-disabled`）を出し、
  「削除」ボタン（`.platform-delete-link`）を出さない。`dashboard.html`の
  SNS連携状況アイコン（`loadSnsStatus()`）も同様に、閲覧者には削除ボタン
  （`.sns-icon-delete`）を出さない。
- サーバー: `/oauth/{instagram,threads,facebook,x,linkedin}/start`（新規連携の
  開始点、ブラウザの`<a href>`によるフルページ遷移で叩かれるGETルート）に
  新設の`blockViewerRoleRedirect`を追加。既存の`blockViewerRole`はJSON 403を
  返す設計でfetch経由のAPI向けのため、フルページ遷移ルートでは
  `blockExpiredTrial`や`requireSnsConnectionAvailable`と同じ流儀に合わせて
  `onboarding.html`へ`res.redirect()`する専用ミドルウェアを新設した。
  `POST /api/sns-connections/:platform/disconnect`は既存の`blockViewerRole`で
  対応済み（変更なし）。`GET /api/sns-connections`（連携状況の閲覧）は
  ロール不問のまま（変更なし）。

#### メンバーを招待する（team.html）

既存実装が招待ボタン（`#invite-open-btn`）をrole !== "管理者"で既に非表示化
しており、`POST /api/team/invite`もサーバー側で管理者ロール限定チェック
（`currentUserRole(req.user) !== "管理者"` → 403 forbidden）を持っていたため、
今回の対応で変更した箇所は無い。閲覧者はこの既存の「管理者以外禁止」に
自動的に含まれる。

#### お支払い方法（payment.html）

- 従来は「管理者以外はセクション自体を非表示にしてreturnする」実装
  （`me.user.role !== "管理者"`）だったため、閲覧者も含め全非管理者ロールが
  ページを一切閲覧できなかった。これを「管理者・閲覧者以外は非表示」に変更し、
  閲覧者の場合はカード一覧の取得（`loadCardList()`）のみ行い、カード追加ボタン
  （`#add-card-btn`）を非表示、`renderCardRow()`の削除ボタンを省略、
  `renderCardList()`のプライマリ／バックアップ入替行（`#swap-row`）を常に
  非表示にする。Stripe.js（`ensureStripeJs()`）は閲覧者パスでは一切呼ばれない
  （追加フォームを開くイベントリスナー自体を登録しないため）。
  承認者・編集者は従来通りページ非表示のまま（変更なし）。
- サーバー: `GET /api/billing/payment-methods`の権限チェックを、
  管理者限定の`requireAdminRole()`から、管理者・閲覧者を許可する新設の
  `requireAdminOrViewerRole()`に変更。カード追加（setup-intent・confirm）・
  削除・入替の4ルートは、元々`requireAdminRole()`（管理者以外を一律拒否）が
  かかっており、これが閲覧者も含めて既にブロックしていたため変更不要と判断した
  （一時的に`blockViewerRole`も併用で追加していたが、`requireAdminRole`と
  役割が重複しエラーメッセージも不整合になるため、実装確認後に削除した）。

## エッジケース・注意点

- `redirectIfViewerForbidden`・`insertRoleNavItems`のnav非表示は、あくまで
  UI上の導線を隠すためのものであり、単体ではセキュリティ境界にならない
  （ブラウザの開発者ツールでDOM操作すれば見た目上は再表示できる）。
  実際の防御は必ずサーバー側の`blockViewerRole`系ミドルウェアが担う。
- `blockViewerRoleRedirect`は「フルページ遷移で叩かれるGETルート」専用。
  fetchベースのAPIには従来の`blockViewerRole`（JSON 403）を使うこと。
  混同すると、fetch側はJSONパース失敗、フルページ遷移側は生JSON画面表示という
  形でUXが壊れる。
